# 語言法 —— 認知階梯與人語層

> 家規第九章的完整論述。條文（第 32–36 條）見 [README.md](README.md)；本文是條文的推導、規格與判例。
> 反面教材：一篇講認知階梯的研究長文，自己沒有認知階梯（存檔於前一個專案，未隨範本帶）。本文就是它的改寫版。
> 傷疤帳本：[LESSONS.md](LESSONS.md)。
> 語感附錄：[AI-TONE-ZH-TW.md](AI-TONE-ZH-TW.md)——本章治的是資訊順序，那一份治的是「順序對了讀起來還是不像人打的」，並列出繁中 AI 腔的三股與各自的擋法。

## 一句話

**AI 私下怎麼想不管；凡是人要讀的文字，先講為什麼，再講做了什麼，最後才是怎麼做的。**

---

## 為什麼需要這一章

從一個真實的早上開始。你打開自己專案的 `docs/10-truth/architecture.md`，想確認系統長什麼樣。第一段就是一張 Stack 表。往下讀到 Gate 2 那節，三行字裡塞了一條 CLI 契約、一條斷言規則、一個「不是另一支指令」的否定邊界、一段「分成兩支的話會怎樣」的反事實辯護——但沒有一句話告訴你**為什麼需要預檢**。`FR-75`、`ledger`、`Gate 2` 三個詞在這份文件裡從未被定義。

這些文件是 AI 寫的，而且每一句都是對的。問題不在正確性，在**順序**：它把你該最後讀的東西放在最前面，把你該最先知道的東西直接省略。你得自己逆向拼圖。

2026-09-05 盤點前一個專案，同樣的病灶找到五處（架構文件兩處、一份 ADR、`CONTEXT.md`、意圖層的原則文件）。這不是個案，是 AI 寫作的預設形狀。這一章存在的目的：說清楚這個病是什麼、為什麼會有、放著不管會怎樣，以及我們的解法。

---

## 病：認知階梯倒置

人讀工程文字有固定的順序需求，像爬樓梯：

1. **Why** —— 這個變更想解決什麼問題？
2. **What** —— 系統的行為因此變成什麼樣？
3. **How** —— 具體怎麼實作的、邊界怎麼守的？

需要深究才往下爬；多數時候讀完 Why 和 What 就能做決定。

AI 的產出把這座樓梯倒過來蓋。它從 How 開始：邊界處理、分支排除、「為什麼不用另一種做法」的防守。因為那段文字根本不是寫給你的——**它是 AI 做完事之後留下的驗證筆記**。它在寫碼時必須想清楚所有邊界才能讓測試變綠，等你叫它「總結一下」，它就把腦內那份筆記原樣倒出來，沒有翻譯成人話。

倒置有三個可辨識的特徵，前一個專案全數命中：

| 特徵 | 長相 | 前一個專案的判例 |
|---|---|---|
| 開場即細節 | 第一段就是表格、檔名、schema 欄位 | 架構文件開場即 Stack 表；原則文件是最上游的意圖文件，第四欄卻是 CLI 指令名 |
| 格言式壓縮 | 有畫面、沒推導的凝練句 | 「會得到一台官僚機器而不是工作流」「做成集合是為了一個不存在的規模」 |
| 防禦性論證 | 講「不做什麼」多過講「做什麼」 | 一份 ADR 四個要點有三個是「不是集合、不合併、要人確認」；`CONTEXT.md` 連續三段「X 不是 Y」 |

要強調一件事：**這些句子難讀，但每一句背後都是一個真實決策。** 「某個實體的決定欄位不帶 status」是有人真的想過要加、然後被否決的。病不在內容，在於結論被壓縮到讀者必須自己補完中間所有推導。

## 成因：它為什麼天生這樣寫

三個原因，都是訓練方式的必然，不是哪次 prompt 沒下好。

**一、預訓練把「人味」當雜訊濾掉了。** 模型的訓練目標是猜對下一個字。人類真實的解釋方式——先鋪背景、適度重複、打個比方、停頓一下——在統計上是高變異的，猜不準；乾淨規整的高密度句子才猜得準。所以模型收斂到後者。你讀起來覺得「少了什麼」，少掉的正是那些被當成雜訊濾掉的引導結構。

**二、對齊訓練獎勵「看起來滴水不漏」。** 給模型打分的機制（人類標註者和 AI 裁判）偏好長的、覆蓋全面的、預先堵住所有質疑的回答。模型學到的教訓是：把「非此即彼」的防禦論據塞好塞滿，分數就高。防禦性寫法不是它的毛病，是它的得分策略。

**三、代理的驗證筆記直接外溢。** 寫碼的 AI 必須在腦內維持一份密集的邊界檢查清單，否則測試過不了。現在的架構沒有把「內部推理」和「對外說明」分成兩個環節，所以叫它寫 PR 描述時，它把清單直接投影出來。這就是為什麼那些文字讀起來像法庭卷宗——它本來就是卷宗。

第三點順帶解釋了一件事：**對 AI 喊「寫白話一點」為什麼沒用。** 抽象的風格指令，代理的違背率高得驚人（實證約 67%）；更糟的是負向指令（「不要防禦性論證」）反而會讓它滿腦子都是防禦性論證。解法不能靠喊話，要靠結構——這是後面「人語層」用硬模板而不用風格描述的原因。

## 放著不管會怎樣：自噬迴路

AI 寫的 PR 說明和文件會沉澱進公開 repo；下一代模型爬這些 repo 當訓練資料，把這種風格當成軟體工程寫作的標準答案；於是寫得更像卷宗，沉澱得更多。迴路一旦閉合，2019 年以前那種階梯式的工程溝通傳統就會被統計性地邊緣化——不是被打敗，是被稀釋到訓練資料裡找不到。

這個迴路在你自己的 repo 裡是縮小版但同樣成立。家規第 4 條說 codebase 是 AI 的 in-context 訓練素材：**你留在 docs 裡的每一份卷宗，都在教下一個 session 的 AI 用卷宗體寫作。** 存量不清，新規則會被存量拖回去。這是本章要求全面重寫存量文件（而不是只管新產出）的理由。

## 解法：人語層（Human Layer)

核心原則一句話：**執行與溝通解耦。** AI 內部推理隨便它由下至上、高密度、滿地防禦——那是它做對事情的方式，不許干涉。但輸出到人眼前的出口處，一律過一道轉換。

### 六個場合，六份必答清單（2026-09-05 修訂：模板降為清單）

人在開發流程裡會讀 AI 文字的地方有六個。初版給每個場合一份硬模板（固定節標題），實跑一天就發現代價：**越表單，越不像人打的**。查證了歷久不衰的開源專案（Linux kernel、git、Go、Rust）怎麼寫——全部是散文，零節標題，Go 甚至明文禁止 Markdown；結構靠的是「第一段先立問題」的段落順序慣例和「必答內容清單」，清單寫在規範文件裡當作者的檢查表，**不寫在產出物裡當骨架**。

所以修訂為：每個場合列出「必須答到的問題」，答到了就好，形式自由。共用的兩條精神不變：**順序先 Why 再 What 再 How；讀者停在任何一段都不漏關鍵資訊**。

| 出口 | 第一屏放什麼 | 細節掛哪裡 |
|---|---|---|
| CLI 即時回報 | 粗體結論一行 ＋ 影響 ＋ 下一步要人做的決定 | 讀者要就問；不主動傾倒 |
| commit | subject 維持 conventional commits；body 首行講 Why | body 下半部；再深的進 PR |
| PR 描述 | 經典模板五節（英文）：Description／Motivation and Context／Behavior／Testing／Notes | 「刻意不做什麼」有固定的家（Notes），不會因為趕時間就消失 |
| docs | 一句話 → 標題化的 Why → 具體失效情境 → 才進表格與規格 | 同文件下半部（判例見本文〈判例：改寫前後對照〉） |
| 上下文重建（隔天接續） | 昨天停在哪、為什麼停、今天第一步 | 指回票與 State 文件 |
| 票（issue／ticket） | 標題＝白話結果句：做完後系統多了什麼；**前 11 字自足**（DAG 圖截斷線）、全長 ≤28 字 | schema 名詞、FR 編號、驗收條件進 body；`## Done when` 承載精確約束 |


### PR 是這一章唯一改回模板的出口

其餘五個場合都是必答清單、形式自由，只有 PR 用固定節次。理由是散文做不到的一件事：**「刻意不做什麼」需要一個固定的家**。寫的人趕時間時，散文會先掉這一段——而那一段往往是審查者最需要的（這個 PR 為什麼不順手把 X 一起改？那是另一張票還是漏了？）。放進 `Notes` 就掉不了。

用的是 2015 年前後 GitHub 的主流模板（Rails、Atom 那一系），不是自創格式——符合第 37 條的使用鏈要求。

兩個從實作中長出來的手法：用 `→` 的流程區塊把**因果距離**畫出來（「產出舊路徑 → 兩步之後被拒收」比一句話更能說明為什麼難查）；既有行為要明確標成 intentional，否則審查者會把它當成這次改壞的。

各場合的必答問題在人語層 skill；本表是摘要。表裡的「第一屏放什麼」讀成「必須答到什麼」，不是「必須長這樣」。

### 術語：用有使用鏈的詞

一個詞是對的，不是因為它字面上合理，是因為**這個圈子的人真的在用它**。AI 造詞時度量的是字面合理性，度量不到「大家實際用哪個」——所以會生出每個字都對、整個詞沒人講的東西（反面教材：把任務圖的分層叫「波次」，中文搜尋只會查到倉庫揀貨；正牌講法是「層」，英文 topological generations，networkx 有同名函式）。規則：

1. 專有名詞先查使用鏈——誰在用、哪個工具的文件、哪本教材。
2. 查得到就用它；中文圈習慣直接講英文的詞，就直接用英文，第一次出現給一句白話解釋。
3. 查不到既有講法才准自創，而且要當場標記是自創。
4. 用詞的天花板：高中生看得懂。

### 語意記號：螢光筆的替代品

終端渲染的是 markdown，沒有真的螢光筆。但螢光筆的認知功能不是顏色，是**可預測的掃讀錨點**——你學會「看到某記號就是某類資訊」之後，掃一眼就能定位。所以用固定記號替代：

- 每次回報**第一行必是粗體結論**——眼睛永遠知道從哪裡開始。
- `⚠ 重複踩點：` 固定前綴——這個坑你以前踩過，帳本裡有案底。
- 關鍵數字、檔名、指令一律 `code span`——掃讀時自動浮起。

記號清單刻意短。記號一多就沒有記號了。

### 救生圈與漏接偵測

`wait-what` skill（「停——剛才那段沒聽懂，重講」）保留，而且被賦予第二個身分：**每按一次 wait-what，就是人語層漏接一次**，事件記入 [LESSONS.md](LESSONS.md)。規則系統自帶失敗回報通道，才修得動自己。

`caveman`（電報體）與人語層互斥——一個砍字數、一個建階梯，方向相反。手動開電報體時人語層讓位，這是使用者的明示選擇。

### 傷疤帳本

重複犯的錯是這本法典最值錢的素材。帳本 [LESSONS.md](LESSONS.md) 記錄：踩了什麼坑、什麼訊號能提早看出來、對策是什麼、犯了第幾次。AI 在任何 session 裡發現眼前的錯與帳本某條吻合時，用 `⚠ 重複踩點：` 當場提醒，並把累犯次數 +1。

這是第 30 條（經驗固化進 CLAUDE.md）的升級：CLAUDE.md 記「這個 repo 的規則」，LESSONS.md 記「這個人和這套方法的傷疤」——後者跨專案、進書。

## 存量清理：兩段式防丟失協定

全面重寫存量 docs 有一個真實風險：那些「X 不是 Y」的格言句背後都是載重決策，重寫時最容易把約束改丟。協定如下：

1. **抽取**：逐檔把每一句防禦性陳述機械展開成一條可核對的約束（「decision 不帶 status 欄位」→ 一條 claim）。
2. **重寫**：依人語層規格重寫全文——約束不刪，只換說法、降層級、補推導。
3. **回核**：逐條檢查約束清單，每條在新文中找到落點。清單附在 PR 裡。
4. **人只核清單**，不逐行讀 diff——diff 只顯示改了什麼，不顯示丟了什麼語意。

一檔一 PR，不一次全上。

## 判例：改寫前後對照

取自前一個專案的架構文件（`docs/10-truth/architecture.md`），本章規則的實地演示。

**改寫前（卷宗體）：**

> `pnpm review approve` 在 Gate 2 前呼叫 ledger 預檢（`FR-75`）：任一 `risk: high` 的 claim 不在 `VERIFIED`／`REMOVED` → 拒絕並逐條列出。**預檢是 `review.ts` 的一部分，不是另一支指令**—— 分成兩支的話跑一次品質檢查就會順手推動狀態（審查指令的既有原則）。

**改寫後（階梯體）：**

> **高風險主張沒查證完之前，內容不能被核准。** 這是為了防一種具體的失敗：一篇文章裡引用的數據還沒驗證，就被人順手按了核准、往下游流。
>
> 所以 `pnpm review approve` 在核准前多做一步預檢：檢查每一條標了高風險（`risk: high`）的主張，是否都已查證（`VERIFIED`）或已刪除（`REMOVED`）。有任何一條不是，就拒絕核准，並列出是哪幾條。
>
> 實作上，預檢寫在 `review.ts` 裡面，不做成獨立指令——因為獨立指令會讓「檢查品質」和「推動狀態」變成同一個動作，而我們定過原則：檢查不該有副作用。（`FR-75`）

字數變多了。這是刻意的：本章優化的從來不是字數，是**讀者到達「可以做決定」所需的秒數**。改寫前的版本要讀者自己補完四層推導；改寫後的版本讓讀者在第一句就知道這段在守什麼，之後每一層都可以選擇不往下讀。

## 本章與其他章的關係

- **第 1 條（人機分工）**：本章是它在語言上的落實——AI 由下至上地想，沒問題；由下至上地**說**，不行。
- **第 4 條（codebase 即訓練資料）**：自噬迴路是它的生態版；存量清理是它的執行。
- **第 28 條（PR 由人把關）**：那條的未定條款「AI 先產 PR 導讀摘要」由本章的 PR 模板正式接手。
- **第 30 條（經驗固化）**：LESSONS.md 是它的跨專案升級。
