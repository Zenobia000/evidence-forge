## 這份文件寫給誰

**已經會用 AI coding、但還交付不穩定的工程師。** 不是產品階段圖，是作戰圖：
一條功能從想法走到可維護，中間每一步該由誰動手、什麼時候必須停。

它只回答四件事：

1. 現在該做什麼
2. 什麼時候交給 AI
3. 什麼時候人一定要介入
4. 什麼情況必須停下來回頭修

## 一句話

**Spec before Scale，Slice before Build，Evidence before Merge。**

先把最小可做規格立起來，再切成小塊交給 AI 做，最後用驗證證據決定要不要往下走。
三句話的順序不能換 —— 換了就會得到那三個熟悉的症狀：文件腐爛、規格漂移、PR 大到沒人審得動。

**口訣**：規格先於開工／切片小於大包／證據先於放行。

## 1. 兩層時鐘

| 時鐘 | 單位 | 邊界動作 |
|---|---|---|
| **切片**（slice） | 一片一個 context，做完 `/clear` | 片末必須回寫文件、附上對應的 AC 與測試 |
| **輪**（round） | 每 2–3 片，或主路徑穩定一次 | 強制過 S5 收斂檢查點（§5） |

分流的原則：**能綁在時鐘上的判斷，綁在時鐘上；綁不上的，寫成中斷。**
片中只處理「必停紅燈」（§3）；其餘一律記帳，輪末一次結清 ——
「現在不處理」也是一個決定，而且多數時候是對的決定。

## 2. 七站，每一站的出場條件

橫軸不是產品生命週期，是**單一功能從想法到穩定收斂**的執行流程。
每一站都有「往下走的條件」與「停下來的條件」，兩者都不成立時，代表你還沒把這一站做完。

### S0 問題定義（探索區）

**目的**：不要一開始就叫 AI 亂做。

- **人做**：定義使用者情境；決定這次只解哪個子問題；**明確寫出不做什麼**
- **AI 做**：整理參考案例、把需求轉成候選 flow、生初版 task brief
- **文件至少要有**：問題陳述、一句話價值、簡版 User Flow
- **往下走**：目標使用者清楚、happy path 清楚、範圍有邊界
- **停下來**：講不出使用者是誰；同一需求有兩種以上互斥理解；成功條件寫不出來

### S1 最小規格（探索區）

**這一步是整張圖的地基。AI 不應該在這之前大規模開工。**

最小規格包：FR（功能需求）、User Flow（主路徑）、AC（驗收條件）、關鍵 SRS（輸入、輸出、限制）。

可用的最小格式：

| 欄位 | 內容 |
|---|---|
| Goal | 這一塊要完成什麼 |
| In Scope | 本次包含什麼 |
| Out of Scope | 本次不做什麼 |
| Happy Path | 使用者如何走完 |
| AC | 什麼算完成 |
| Risk | 有哪些不可踩的線 |

- **AI 做**：把自然語言整理成規格模板、補遺漏欄位、列可能的 edge case
- **人一定要決定**：需求取捨、商業規則、權限與資料模型、API 是否可變
- **往下走**：AC 可驗收、happy path 有步驟、風險邊界已註明
- **停下來**：AC 無法被測試；規格還停在口語狀態；流程畫不出來

### S2 切片規劃（建造區）

這一步決定後面會不會爆炸。核心是**垂直切片**（細節見 [GRANULARITY.md](GRANULARITY.md)）。

一個切片必須：可獨立驗收、可獨立測試、PR 不大、對應至少一條 AC。

- **人做**：切成 1–3 天內可完成的小塊；決定優先序；指定每片的 AC 與測試方式
- **AI 做**：拆 task、建議依賴順序、預先生 checklist 與 test case
- **往下走**：每片都說得清楚 Done 是什麼、都能對應規格、PR 預估不會太大
- **停下來**：切片橫跨太多模組；一片裡有太多未知數；一片做完無法驗收

### S3 AI 實作（建造區）

- **AI 適合做**：scaffold、小範圍功能實作、補測試、重複性 refactor、文件同步草稿、變更摘要
- **人不要放手的點**：API breaking change、資料模型改動、權限與安全、跨模組架構決策、UI/UX 大改
- **實作規則**：先做主路徑不追複雜互動；一次只給 AI 一片；每片必須附規格來源與 AC；每次提交都帶測試與變更說明

### S4 驗證回補（建造區）

**測試不是最後才做，每個階段都測，只是深度不同。**

| 階段 | 測什麼 |
|---|---|
| S0 | 不測 code，確認需求講不講得通 |
| S1 | 規格審查、AC 可測性 |
| S2 | 測試案例設計 |
| S3 | smoke test、happy path |
| S4 | function test、integration，必要時 visual diff |
| S5 | contract／E2E 主路徑 |
| S6 | regression、收斂驗證 |

關鍵原則：每個測試要能追溯到某條 AC 或 SRS；測試紅燈時要知道是哪條需求失效；
**不接受「測過了但不知道在測什麼」**。

### S5 收斂檢查點（收斂與穩定區）

**防止文件腐爛的核心節點。每完成 2–3 個切片，或主路徑穩定一次，就進一次。**

檢查四件事：

```
□ Code ↔ Spec 是否一致
□ Spec ↔ Test 是否可追溯
□ PRD／Flow／SRS 是否已被現況更新
□ 該收斂了，還是可以繼續疊功能
```

進入 S6 的觸發條件：同一路徑反覆重做；多人協作開始互撞；API／state／data 邊界開始不穩；
文件落後於程式；PR 常常需要口頭補充才看得懂。

檢查點的存在理由：把「要不要停下來整理」從施工中的意志力問題，變成輪末的例行公事。
**你不需要在戰鬥中判斷何時打掃 —— 戰鬥結束一定打掃。**

### S6 重整收斂（收斂與穩定區）

不是大修特修，是**把探索成果正式化**：PRD baseline、SRS baseline、API 契約收斂、
模組邊界重整、ADR 記錄、補 NFR 的核心項目。

意義只有一個：**防止 AI 繼續在鬆散的地基上亂長**，把「可做」變成「可維護」。
做完回 S2 重切下一輪。

## 3. 紅黃綠燈

| 燈 | 意義 | 動作 |
|---|---|---|
| 綠 | 規格清楚、可驗收、證據齊 | 往下一步 |
| 黃 | 功能可做，但文件未同步或流程仍不穩 | 允許前進，但先補文件或補測試 |
| 紅 | 規格不明、重做過多、breaking change、測試不可追溯 | 停下來，回上一個節點 |

### 必停紅燈（沒有例外）

- AI 改了資料模型但沒更新規格
- AI 改了 API contract
- 同一個功能第三次重做
- PR 大到無法審
- 測試失敗但追不到是哪條需求
- 文件描述與畫面／程式行為不同

## 4. 四個回圈

回頭不是失敗，走錯的回頭路才是。圖上四條回圈都有箭頭：

圖上四條回頭的線都標了字母，跟這張表對得起來：

| 回圈 | 圖上的標記 | 路徑 | 什麼時候走 |
|---|---|---|---|
| A 需求澄清 | `A｜AC 寫不清` | S2 → S1 | AC 寫不出來、規格講不清就回去補 |
| B 切片 | `B｜修到綠` | S3 ↔ S4 | 一片做完、測完、修完，才進下一片 |
| C 收斂 | `C｜重切下輪` | S4 → S5 → S6 → S2 | 功能變多之後回頭補文件、補契約、補結構 |
| D 中斷 | `D｜修完回主線` | 任何節點 → 停下理解 → 重新插隊 → 回 S2 | AI 失控、文件腐爛、規格漂移 |

事故型回退只有一種：合併後發現壞掉 → revert 開票重做。revert 也是一片，也排進依賴圖。

## 5. 中斷向量表（四個吃經驗的判斷）

訊號分兩級：**斷路級**＝立刻停止產碼、切換模式；**記帳級**＝記下來，輪末處理。
（記到哪裡由新系統決定——舊的 `docs/20-state/open-issues.md` 已經不在了。）

### U — 停下來重新理解（全部斷路級）

四個判斷裡唯一「出現就停」的，因為每個訊號都代表**人已經跟不上系統**，繼續產碼是在擴大不理解的面積。

| 訊號 | 依據 |
|---|---|
| 兩次法則用完仍失敗（升級推理／換模型後還是不行） | 第 17 條失效＝問題不在模型，在你對問題的理解 |
| 你答不出「這功能走哪個接口、觸發時機是什麼」 | 第 16 條失守，你已從監工退化成祈禱者 |
| AI 出現偽造徵兆（謊稱測試通過、編造結果） | 第 29 條 |
| 人審 PR 時看不懂 diff 在幹嘛 | 第 28 條的前提崩了 |

**動作**：停止產碼 → 開「理解 session」（唯讀，不准改碼）：讓 AI 導讀鏈路、把程式碼對應回需求編號、
把對不上的地方修進文件 → 修完才回主線。

### R — 重構

| 訊號 | 等級 |
|---|---|
| AI 說「上下文和我預期的不一致，讓我重新看看」出現第 2 次（同一區域） | 斷路級 —— 它自己都讀不懂自己寫的碼了 |
| 一片的改動碰到 ≥3 個不相關模組 | 記帳級 |
| 同型程式碼第 3 次出現（rule of three） | 記帳級 |
| 一片的實際 session 數連續兩片超過估計 | 記帳級 —— 結構在拖慢所有人 |

**動作**：重構開成**票**，排進依賴圖 —— 不順手重構。順手重構＝在別人的票裡夾帶自己的決定，
PR 會超出它的描述。斷路級的例外：先開票、把當前片標 blocked、重構票插隊（圖上的「重新插隊」）。

### D — 文件清整

| 訊號 | 等級 |
|---|---|
| 新 session 開工被文件**誤導**（文件說謊） | 斷路級 —— 說謊的文件比沒有文件毒，它會變成 AI 的錯誤訓練素材（第 4 條） |
| 追溯表出現紅（`@covered-by` 指向不存在的檔案、編號斷鏈） | 斷路級 |
| State 文件混進了規格敘述 | 記帳級 |
| 同一件事在 ≥2 份文件重述 | 記帳級 —— 下次只會改到一份 |

判準一句話：**下一個沒看過對話的 agent 讀這份文件，會不會被帶錯路？**

### I — Infra 升級（CSV/SQLite → 正式架構）

**這個判斷沒有斷路級 —— infra 永遠不在輪中升級**，只在 S5 用三問評估：

1. schema 連續**兩輪**沒有改動？（業務形狀穩定了）
2. 出現簡易儲存**做不到**的具體需求？（並發寫入、關聯查詢、資料量）——「感覺不專業」不算需求
3. 資料開始有「丟了會痛」的價值？（真實使用者、真實內容）

**三問中兩題 Yes 才升級**；升級本身開一份規格走 S2，升級後回 S3 重跑最薄的一條路。
一題 Yes 都沒有卻想升級的，通常是想逃避產品問題去做舒適的工程問題 —— 記帳，下輪再問。

## 6. 六條法寶規則

1. **沒有最小規格，不要叫 AI 大量開工**
2. **一個切片只做一條可驗收功能**
3. **每次提交都附上對應的 AC 與測試**
4. **每 2–3 個切片一定做一次收斂檢查**
5. **涉及契約、資料模型、安全，一律人審**
6. **文件跟 PR 一起更新，不准事後補**

**心法**：像教人蓋房子，不是一直叫機器搬磚 —— 先畫小區塊，每蓋一段就檢查有沒有歪，歪了先修，再往上蓋。

## 7. 這張圖跟三環圖怎麼拼（縮放層級）

兩張圖講同一台機器的兩個縮放層級，不是兩件事：

| | 本圖（FLOW） | 三環一真相（已隨重置移除，見 `main` 的歷史） |
|---|---|---|
| 講什麼 | 一條功能從問題定義到可維護的**賽程** | S3–S4 建造迴圈這一段的**引擎室** |
| 時間單位 | 輪（2–3 片，或一次主路徑穩定） | tick（一次 `/loop` 觸發） |
| 誰在動 | 人與 AI 換手推進階段 | 三個 session（排程／建造／審核）繞著 GitHub 真相自轉 |
| 接縫 | S2 產出帶依賴的切片 → 餵給三環；全部切片關掉 → 進 S5 | 排程環讀的依賴圖來自 S2；審核環的判決落地靠人在 S4 之後按合併鍵 |

一句話記法：**FLOW 決定「現在是哪一站」，三環決定「這一站裡誰在轉」。**
審核環的業界對照與五個強化，見 [LOOP-REVIEW.md](LOOP-REVIEW.md)。
分支怎麼跟上 main、怎麼進 main，見 [GIT-FLOW.md](GIT-FLOW.md)。
