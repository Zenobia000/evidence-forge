# 模型路由：從便宜的開始，撞牆才升級，每一次都記帳

> 法在[家規第 43 條](README.md#第七章-流程法敏捷票務平行化)，這裡是它的展開、初始配比與帳本。
> 起因：前一個專案要在開發裡順便量一件事——**不同模型與推理強度（effort）怎麼搭，最省又做得完**。結果放在最後一節〈前一個專案的統計〉。
> 模型的定位與牌價會變，引用前先回官方頁核對；下面的模型名與價格只是寫下這份時的例子。

## 一句話

**每張票從「推得動它的最便宜組合」開始，撞牆才往上升一格；升級與結果都記在帳本上，下一張同類的票試著降一格。**
配比不是一次想好的，是從帳本裡長出來的。

## 為什麼

- **最強的模型不是預設值，是上限。** 每張票都用最強的模型，花費會是必要的好幾倍，而且量不出「其實便宜的就夠」。
- **推理強度（effort）是比換模型更細的旋鈕。** 同一個模型把 effort 調低，常常就夠做例行工作；官方的建議也是先試同一個模型的較低 effort，再考慮換模型。
- **初始配比是判斷，不是事實。** 一開始照「錯了代價多高、推理鏈多長、有沒有範本可抄」分派；帳本累積之後，拿數字取代判斷。

## 可用的組合（由便宜到貴）

**為了讓專案一開始的成功率高，只開三格。** 更便宜的組合（較低 effort、更小的模型）等帳本證明某一類工作在格 1 一次就過得很穩，再討論要不要開放；要開放必須使用者點頭。

| 格 | 定位 | 例（寫下這份時） | 對應的子代理角色 |
| --: | --- | --- | --- |
| 1 | 便宜快 | Claude Sonnet，effort high | `.claude/agents/builder-sonnet-high.md` |
| 2 | 強 | Claude Opus，effort high | `.claude/agents/builder-opus-high.md` |
| 3 | 最強（上限） | Claude Opus，effort xhigh | `.claude/agents/builder-opus-xhigh.md` |

- 比格 3 更貴的模型不用；要用必須使用者點頭，並在帳本記理由。
- 在 Claude Code 訂閱裡花的是用量額度，不是帳單，但比例一樣。
- 子代理的模型與 effort 用 `.claude/agents/*.md` 的 frontmatter 定成三種固定角色，派工時選角色，不在提示詞裡臨時指定。換模型時改那三個檔的 `model`／`effort`，這份文件跟著改例子。

## 初始配比（判斷的起點）

| 工作的樣子 | 起始格 | 例子 |
| --- | --: | --- |
| 範圍清楚、有現成程式或畫面可抄；機械性工作 | 1 | 照設計稿刻畫面、補測試、搬檔改名、刪掉不用的東西、改字串、只讀的清點 |
| 一般功能、要自己設計一點 | 1 | 一個新畫面、一組 CRUD、一條規則引擎、一次測試收斂 |
| 地基、錯了代價高、推理鏈長 | 2 | 專案骨架、資料格式與遷移、使用者資料的讀寫、權限與金鑰、牽涉錢的計算、要判讀大量規劃文件的整理 |
| **新的外部供應商轉接器**（串流、重試、計費、各家錯誤碼） | 2 | 前一個專案的反例：格 1 修了三、四輪，token 是格 2 的兩倍多（見〈前一個專案的統計〉） |
| 除錯卡住、跨片整合出錯 | 3 | 視情況 |

審查也照同一張表：T1／T2 的 Claude 審查用格 1；T3 的 Claude 審查用格 2；換家模型的交叉審查（例：Codex）用中等推理強度，只報必修。
**審查者不必比實作者強**——換一家模型帶來的盲點差異，比同一家的更強模型有用（家規第 39 條的配套）。

## 什麼時候升級、什麼時候降級

升一格的訊號（任一個）：

1. 同一張票的測試**連續兩次**沒過，而且第二次不是因為外部原因（網路、環境）。
2. **途中自評**：實作到一半，子代理自己判斷「這張票比它被分到的格難」——例如要改的檔案比票寫的多一倍、遇到票沒預料到的設計決定、同一處改了第三次。子代理在回報（或中途訊息）裡寫一行「升級訊號：途中自評，理由……」，派工者決定升不升。
3. 第一輪審查的**必修 ≥ 3 條**。
4. 卡住：同一個錯誤重複出現、或開始改不相關的檔案（家規第 29 條的撞牆徵兆）。
5. UAT 沒過，而且原因是邏輯錯，不是規格沒講清楚。

**為什麼要有「途中自評」**：前一個專案第 3 條訊號亮了 16 次，一次都沒升——因為審查在實作完成後才跑，訊號亮的時候票已經做完了，升級只剩「重做」這個選項，而重做沒有人想選。升級訊號要在**還來得及換人**的時候亮，所以把自評放到途中，排在審查之前。

規則：

- **做到一半不降級**：換模型會丟掉它對這張票的理解。
- **升級要記帳**：哪張票、從哪格到哪格、哪個訊號觸發。
- **訊號亮了沒升，也要記**：寫「訊號亮、沒升，理由……」。沒記的話，帳本會說「從來不需要升級」，而那不是事實。
- **下一張同類的票試降一格**：這是實驗的另一半；只升不降，量到的永遠是上限。
- **連續兩張同類的票在某一格一次就過，就把那一格定為那一類的新起點**，寫回上面的初始配比表。

## 要記什麼（帳本）

每張票結束時記一列。數字從子代理的回報、CI 與審查紀錄取，不憑印象（`LESSONS.md` L-012）。

| 欄 | 說明 |
| --- | --- |
| 日期 | 結束那天 |
| 票 | 票號與切片編號 |
| 類別 | 上面「工作的樣子」的哪一類 |
| 起始格 → 最終格 | 例如 `1 → 2` |
| 升級訊號 | 觸發的是哪一條；亮了沒升也寫；沒亮就空白 |
| token | 子代理回報的用量（實作＋修審查，分開寫） |
| 測試失敗次數 | 到綠為止紅了幾次；環境造成的另外註明 |
| 審查必修數 | Claude＋交叉審查第一輪 |
| UAT | 過／沒過／未驗 |
| 備註 | 一行 |

## 失效模式

- **只升不降**：每張票都升到上限，帳本只證明「貴的也做得完」。降級那一步不能省。
- **把升級歸咎於模型**：很多「做不出來」是票寫得不清楚。升級前先問：換成人讀這張票，做得出來嗎？做不出來就改票，不是升模型。
- **量錯東西**：只看 token，不看測試失敗與審查必修，會選到「便宜但要人收拾」的組合。成本要算到**一張票真正完成**為止。
- **訊號來得太晚**：升級訊號全部排在實作完成之後，等於沒有升級這個選項。見上面〈途中自評〉。

## 前一個專案的統計

> **範例資料，來自前一個專案**（一個 TypeScript 全端應用，約 85 張有完整紀錄的票，2026-09-29～10-05）。給新專案一個起點的感覺，不是新專案的基準——新專案的帳本長出來之後，拿自己的數字取代它。

| 格 | 票數 | 平均 token | 中位數 | 第一輪必修平均 |
| --- | --: | --: | --: | --: |
| 1 便宜快 → 1 | 65 | 335k | 273k | 0.89 |
| 2 強 → 2 | 19 | 378k | 317k | 2.89（難的票才派，選擇偏差） |
| 2 → 3 最強 | 1 | 678k | — | — |

讀法：

- **格 1 撐住了大多數。** 65 張從格 1 開始的票全部在格 1 收完，包括幾張照路徑算 T3 的票。
- **格 2 的必修平均比較高，不代表格 2 比較差**：派到格 2 的本來就是難的票（選擇偏差）。
- **升級只發生 1 次**（一張牽涉金鑰與花費的地基票，2 → 3）。**第一輪必修 ≥ 3 的升級訊號亮了 16 次，但都沒升**，因為審查在實作完成後才跑、訊號來得太晚——所以這份範本把「途中自評」加進升級訊號。
- **反例**：新供應商轉接器類的票從格 1 開始，修了三、四輪，token 是格 2 同類票的兩倍多（思考 token、串流截斷、重試三件都跟錢有關）。這類從格 2 開始。
