# LESSONS —— 傷疤帳本

> 記「這個人和這套方法的傷疤」：重複犯的錯、能提早看出來的訊號、對策、犯了第幾次。
> 與 CLAUDE.md 的分工：CLAUDE.md 記單一 repo 的規則；這裡記跨專案的教訓。
> 與 [PLAYBOOK.md](PLAYBOOK.md) 的分工：**這本記 AI 漏接了什麼，那本記人該調用什麼**。
> 每個坑的背面都有一個人本來該有的問句（這裡記「守衛只擋了一半」，那裡記「問它漏的是哪一半」）——
> 那個問句寫進 `PLAYBOOK.md`，而且只能從這本已經有的條目來，不准憑空造。
> 規則出處：[LANGUAGE.md](LANGUAGE.md) 傷疤帳本節、家規第 30／35 條。
>
> **範本附帶的 24 條來自前一個專案。** 首犯日期與累犯數留著，因為那是「這條有多痛」的證據；
> 例子裡的檔名、票號換成了泛稱。新專案從 L-025 接著記，踩到這 24 條的照樣 +1。

## 怎麼用這本帳

**不要整本讀。按手上要做的事撈兩三條，其他的不看。**

理由是量測出來的：教訓全量灌進 context 反而讓判斷變糊——輸入越長，模型連簡單任務都變不可靠，而規則、票、舊條件混在一起之後，它分不清哪一段還生效，於是在互相矛盾的東西之間取平均。[ERL（arXiv:2603.24639）](https://arxiv.org/html/2603.24639v2)的消融實驗結論是「**選擇性檢索是必要的**」；[DeltaMem（arXiv:2606.03083）](https://arxiv.org/html/2606.03083v1)指出扁平的規則檔會線性膨脹。完整對照見 [GRANULARITY.md](GRANULARITY.md)。

### 記帳規則

- AI 在任何 session 發現眼前的錯與某條吻合：輸出 `⚠ 重複踩點：<條目標題>` 當場提醒，並把該條「累犯」+1、補一行案發紀錄。
- 使用者按 `wait-what`（沒聽懂、要求重講）＝人語層漏接一次，記入 L-002。
- 新條目要件：坑、訊號、對策，三項缺一不記——沒有訊號的坑防不了，沒有對策的坑記了也白記。
- **每條要有狀態**，三態：
  - `現役`——只靠人和代理記得住才不會犯，要撈進 context。
  - `降頻`——已經有閘門擋掉主要路徑，但還有沒擋到的縫；狀態欄要寫**擋住的是哪一段、漏的是哪一段**。
  - `退役`——已被 hook 或測試完全接管，人不必再記。退役條目移到檔案末的 `## 已退役` 區，正文不再撈。
- **退役要有出處**：寫出是哪支 hook、哪條測試接管的。沒有出處的退役是把坑忘掉，不是把坑補起來。
- **累犯紀錄最多留最近三筆**，更早的壓成一行「更早：N 次，最早 YYYY-MM-DD」。次數要留（那是這條有多痛的證據），現場描述不用全留——帳本膨脹本身就是它失效的方式。
- **這份帳本自己的修改，跟它記的教訓走同一條路**：改完當場提交，不要留在工作目錄裡（見 L-002 第 5 筆）。

### 數字怎麼數

帳本裡的數字會觸發動作，所以它要能被兩個人數出同一個結果。前一個專案就有一次審查拿同一份文件數出不同的數字——一個數事件總數、一個數同一型，而兩種數法的門檻會在不同的時候滿。

1. **「累犯」＝帳本裡列得出來的實例總數，含首犯。** 首犯是第 1 次，不是第 0 次。只有首犯的條目，累犯是 1。
   實例可以是「案發紀錄」那種一筆一行，也可以是**巢狀列在首犯底下的編號項**（`L-007`、`L-011` 是這種）——
   兩種都算，因為兩種都數得出來。`L-007` 的首犯底下列了五項、後面又記了一筆，所以累犯是 6。
   被壓成「更早：N 次」的那一行也算進總數。
   **內文的次數要跟列出來的項數一致**：前一個專案有一條寫「一天之內出現四次」卻列了五項，另一條累犯寫 1 卻列了兩項，都是被機器數出來的。
2. **每一筆標型，型的名字寫出來。** 型是這一筆「錯在哪個機制上」的短名（例如「用票號當名詞」「先講機制才講結論」），不是它發生在哪一顆 PR 上。沿用既有的型名，真的不一樣才創新的。
3. **同型序號必須數得出來**：寫「同型第 N 次」的時候，前面那 N−1 筆都要在帳本裡找得到。找不到就不能寫 N——那是一個沒有人能驗的門檻，而它會靜靜地永遠不滿或提早滿。

### 累積型的對策怎麼觸發

「累積 N 次同型 → 做某事」這種對策（目前只有 `L-002` 有），滿的那一筆後面要接一句 **`觸發：做了什麼`**，寫出改到哪一份檔案。沒有那一句，門檻等於沒有滿——**規則自己不會提醒自己**，那正是 L-007 的形狀。

門檻沒滿但痛得夠清楚時可以提前修，那也要寫出來（`提前修，不是門檻觸發`），免得下一個人把它當成觸發紀錄去反推計數。

### 選填欄位

坑、訊號、對策是必填。除此之外帳本用過 **事件**、**例外**、**連帶**、**連帶對策**、**反例**、**備案**——這些都是選填，**缺席不代表不適用**，只代表寫的人當時沒有東西可寫。要判斷某一條有沒有某種資訊，讀內容，不要靠欄位在不在。

### 條目格式

```markdown
## L-NNN 一句話講出坑的形狀（標題也是檢索鍵）

- **狀態**：現役／降頻（擋住哪段、漏哪段）／退役（被誰接管）
- **首犯**：YYYY-MM-DD。發生了什麼、誰抓到的。
- **累犯**：N（含首犯）
  - YYYY-MM-DD（第 N 次，型：…）：…
- **坑**：為什麼會犯——機制，不是個案。
- **訊號**：事前看得到的徵兆。
- **對策**：下次怎麼做；能降成 hook 或測試的就降。
```

## L-001 文件寫成 AI 卷宗體，人讀不懂自己的系統

- **狀態**：現役

- **首犯**：2026-09-05。盤點確診五處：架構文件開場即 Stack 表、一條閘門的說明三行塞五件事、一份 ADR 連列三個「不做什麼」、`CONTEXT.md` 三連「X 不是 Y」、意圖層文件寫滿 CLI 指令名。
- **累犯**：3
  - 2026-09-05（第 2 次）：幾顆 PR 的描述引用「家規某章／LANGUAGE.md」當法源，但該檔案尚未 push——GitHub 審查者點不開的引用＝未定義符號。抓到者：使用者反問「PR 寫法照 lesson 需不需要調整」。
  - 2026-09-07（第 3 次）：一份盤點文件連了一個還在功能線上、沒進 `main` 的檔案，又引「家規第 N 條」當判準，而那份文件的分支基於 `main`。**這次被連結檢查當場擋下**：閘門有效，但它只擋得住 Markdown 連結，「家規第 N 條」那種純文字引用它看不見，是自己回頭清的。
- **坑**：AI 產出的 docs 每句都對，但順序倒置（How 先於 Why）、符號未定義、格言無推導——回頭讀的時候要逆向拼圖。
- **訊號**：文件第一段就是表格或檔名；連續出現「X 不是 Y」句式；出現全 repo 只出現一次且零解釋的專有名詞。**引用一個此刻只存在於自己工作目錄或別條分支的東西**——寫的人點得開，讀的人點不開；連結檢查擋得住連結形式的，擋不住「第 N 條」「見某某文件」這種純文字引用。
- **對策**：人語層五出口模板（LANGUAGE.md）；存量走兩段式防丟失協定。

## L-002 人語層漏接紀錄（wait-what 事件簿）

- **狀態**：現役・高頻

## L-003 重寫補 Why 時捏造事實

- **狀態**：現役・高頻（累犯 9，開任何寫作／開票的工都要撈）

- **首犯**：2026-09-05，一份 ADR 重寫。把「架構與輸入表單沒連起來、切換要重打自由文字」錯寫成「架構被寫死在流程裡」——為了敘事順暢，編了一個更戲劇化但與來源相反的問題陳述。獨立驗證代理比對規劃文件抓出。
- **累犯**：9
  - 2026-09-11（第 9 次，型：拿二手摘要當原文的主張講，同型第 2 次）：拷問選項的建議理由，引的是一顆 commit 訊息裡對兩份分析的轉述，並從它推出結論；原文當時不在 repo，我**沒有講出原文讀不到**。原文進 repo 之後，它的處方接近被標成「沒選」的那個選項。摘要本身沒錯，錯在把摘要裡的一句話當成原文的結論。抓到者：自己讀到原文時發現。
  - 2026-09-06（第 8 次，型：把「我量到的」寫成「我證明了」）：PR 的 Testing 段寫「三次全跑各紅一兩支不同的測試，是我自己開兩台測試伺服器造成的負載，**不是程式問題**」。量到的東西是真的，但只排除了「這顆讓它變慢」，排除不了回歸——**負載夠高的時候，回歸也會表現成隨機紅**。真正能排除的是同負載下跑 `main` 的對照，而我沒有做。
  - 2026-09-06（第 7 次，型：查無路徑當成查無此字）：開票時寫「全域搜某個欄位，**零命中**」「沒有任何畫面顯示它」。實際上兩個元件都在讀它。錯因是 grep 的路徑**不存在**，而 grep 對不存在的路徑不會讓 pipeline 失敗。
  - 更早：5 次（第 2–6 次，全部 2026-09-06）。形態依序是——寫票時捏造前提（說上游快照的技能「可以動」）、轉述時丟失限定詞（把「照第 N 條**的精神**」寫成「照第 N 條」）、沒比對就宣稱「三處一字不差」（實際是六項對四項）、拿二手摘要當論文的主張講（論文的結論與我寫的相反）、出處掛錯（一條規則掛了撐不住的「家規第 27 條」，見 L-011）。**第 2–5 次有三次是獨立審查代理抓的，撰寫者自核一次都沒抓到。**
- **坑**：人語層要求每段補「為什麼」，但原文沒寫 Why 時，改寫者會傾向「編一個合理的」——編出來的往往比真相更戲劇化，且讀起來毫無破綻。開票時同理：為了讓票可以動工，會順手補一句「這個可以改」。
- **訊號**：搜尋**零命中**就下結論。機制在退出碼：`grep` 是三態——0 找到、1 沒找到、**2 出錯**（路徑不存在、權限不足）。多數人只記得 0 跟 1，於是 `grep || true` 把真正的錯誤一起吞掉，而「路徑打錯」就是把 2 讀成了 1。工具層的 Grep 對不存在的路徑**靜默**回零命中，shell 的 `grep` 會**印錯誤並 exit 2**。零命中要當結論之前，先 `ls` 那個路徑，或先搜一個一定命中的字（例如 `import`）。
- **訊號**：新增的問題陳述沒有出處引用；**出現「一字不差」「完全一致」「三處都是」這種一致性斷言**——它讀起來像已經比對過了，而它最常出現在沒比對的時候；Why 讀起來「太順、太典型」（真實的痛點通常更具體、更難看）；票的 Notes 裡出現「可以動」「不受限」這類權限判斷卻沒引規則出處。**轉述的來源是搜尋結果的摘要、別人的整理、或工具回給你的節錄，而不是那一頁原文**——摘要已經幫你做完「這在講什麼」那一步，所以它讀起來像結論；而它最會自己補上的，正好是原文最常沒有的三樣：根因、適用範圍、workaround。（2026-09-09 追一個上游 issue 時又遇到一次同形狀的摘要，三條斷言在原文裡一條都找不到——那次在寫出去之前攔下來了，所以**不計累犯**，只把訊號補在這裡。人這一側的對應卡是 `PLAYBOOK.md` 的 `P-007`。）
- **對策**：改寫新增的每一條 Why 必須帶出處（檔案＋節號）或明標「推測」；獨立驗證代理（非撰寫者）逐條溯源——撰寫者自核抓不到自己的腦補。

## L-005 堆疊 PR 的合併順序給反了，工作靜靜消失

- **狀態**：現役（已成文為家規第 27 條，但沒有閘門查 `baseRefName`——成文不等於硬擋）

- **首犯**：2026-09-06。子 PR 的 base 是父分支，我給的合併順序是「先合父（→main）再合子（→父）」。父分支先進 main 之後，子 PR 才合進父分支——那些 commit 停在原地，隨後父分支被刪。工作沒有進 main，而 `gh pr view` 顯示 MERGED、issue 也被我手動關掉，帳面上看起來是完成的。
- **累犯**：1
- **坑**：堆疊分支（子 PR 指向父分支而非 main）必須**先合子進父、再合父進 main**。反過來做不會有任何錯誤訊息——GitHub 照樣顯示合併成功。
- **訊號**：PR 的 base 不是預設分支；`Closes #N` 沒有自動關票（那是同一個原因的另一個症狀，當時我只補關票，沒有追問為什麼）。
- **對策**：給合併指令前，先查每一顆的 `baseRefName`；base 不是 main 的一律排在它的父分支之前。合併完驗證產物真的在 main 上（`ls` 或 `git log --oneline main -- <路徑>`），不要只看 PR 狀態。

## L-006 在共用工作目錄上做 git 狀態變更，捲走別人未提交的工作

- **狀態**：現役・降頻（`guard-git.sh` 的「HEAD 須等於 PR head」已擋掉主要路徑，拒絕訊息也點名本條；仍未擋 `stash`／`reset`，也擋不住「別的 session 切走分支」——這一段真的踩過，見第 2 次）

- **首犯**：2026-09-06。派審查代理驗 PR 時，交辦文寫「先 `gh pr checkout <n>` 讓 HEAD 對齊 PR head 再跑本機驗證」。代理照做，於是在**多個 session 共用的主工作目錄**上 checkout，順手把另一個 session 未提交的 hook 修改 stash 起來，repo 停在 detached HEAD。對方是排程醒來、發現檔案內容變回舊版才知道——沒有任何訊號。
- **累犯**：2
  - 2026-09-09（第 2 次）：**方向相反的那一半。** 首犯是「我動了別人」，這次是「別人動了我」。我在主目錄 `git checkout -b <新分支>`，當下 HEAD 卻不在 `main`——另一個 session 早已切到它自己的分支，所以我的新分支從一開始就指到對方的 commit。接著對方把 HEAD 拉回 `main` 並 pull，我隨後的 `git commit` 就**落在保護分支 `main` 上**，而 `git push -u origin <我的分支名>` 把對方三顆已合併的 commit 推成了一條新的遠端分支。沒有任何一步報錯。抓到的方式是 commit 輸出那一行——它印的是 `[main 7fb63bd]`，跟我以為的分支名不一樣。損害：零（先用 `git branch <保險名> <sha>` 留了 ref）。
- **坑**：主工作目錄是共用資源。`checkout`／`stash`／`reset` 都會影響別人正在改的東西，而且**不會通知任何人**。
  第 2 次補上另一半：**共用目錄裡，「我現在在哪條分支」是一個會過期的答案**。`git branch --show-current` 只描述問的那一瞬間，而開分支到提交之間隔著讀檔、編輯、跑檢查——那段時間足夠別人把 HEAD 搬走三次。危險的不是切分支這個動作，是**兩次 git 動作之間的那段假設**。
- **訊號**：交辦文裡出現「在主工作目錄上切分支／暫存」這類指示；代理回報「為了拿乾淨的樹所以 stash」；`git stash list` 出現不是自己建的項目。**`git commit` 印出來的 `[分支名 sha]` 跟你以為的分支不一樣**——那一行是唯一會出聲的地方，而它長得像例行輸出。還有：`ps` 看得到不只一個 `claude` 行程；`git reflog` 出現自己沒下過的 `checkout`／`pull`／`cherry-pick`。
- **對策**：派任何會動 git 狀態的代理，一律用 `isolation: "worktree"` 或明確指示開 `git worktree`；**驗證 PR 要在 worktree 裡 checkout，不在主工作目錄**。只讀的代理（grep、gh api、讀檔）不受此限。
- **對策（第 2 次補）**：**確認 HEAD 不是對策，開 worktree 才是。**「提交前再看一次分支」只是把假設的有效期從十分鐘縮到十秒，競態還在（`L-002` 證明過：加一句話防不了結構性的問題，見 `P-005`）。規則改成一句沒有例外的：**只要這次工作會產生 commit，第一個動作就是 `git worktree add`，不在主目錄開分支。** 主目錄留給唯讀與跑檢查。
- **連帶對策**：**修復建議本身也可能是攻擊面**。錯誤訊息若寫「commit or stash」，在共用 checkout 裡就是錯的建議——stash stack 也是共用的。凡是要人「清乾淨工作區」的訊息，都要改成「提交，或從乾淨的 worktree 跑」。
- **例外（什麼時候可以動別人的東西）**：擁有者明示同意 **且** 自己驗證過內容確實被取代——兩個條件都齊才動。驗證方式：`grep -Fxv -f <已提交版本> <工作區版本>`，輸出為空才算涵蓋。

## L-007 守衛只擋了一半，而漏掉的那半無聲

- **狀態**：現役

- **首犯**：2026-09-05／06，一天之內出現五次同形狀的事故，全部是「檢查了條件的一半，另一半靜靜通過」：
  1. **看板繞過閘門**：檢查「狀態轉移合不合法」，沒檢查「前置條件過了沒」。CLI 那條路會擋，畫面這條不會，而人天天走不擋的那條。
  2. **假缺口活了很久**：測試檢查「未達成有沒有掛票號」，從不問「那張票關了沒」。20 條需求標著未達成而票全關了，測試全綠。
  3. **審查標籤不綁 commit**：閘門檢查「有沒有審查通過的標籤」，沒檢查「標籤指的是不是這一版」。標籤貼完 84 秒後推的新 commit，閘門照樣放行。
  4. **repo 比對區分大小寫**：守衛擋了「欄位缺席」（硬錯誤），沒擋「大小寫不同」（整批悄悄落空）。GitHub 的 `owner/name` 不分大小寫，而離線資料是人手寫的。
  5. **欄位只驗有沒有斜線**：擋了「欄位不存在」，沒擋「存在但形狀不對」。`"/"` 過得了關，之後每一筆比對都拿一個不存在的名字去比，整批落空——症狀跟「真的沒有資料」長得一模一樣。
- **累犯**：6
  - 2026-09-09（第 6 次）：**這次是守衛自己。** `guard-git.sh` 的 T3 分級讀完 PR 的檔案清單，餵進判斷迴圈前跑了一次 `tr -d '<換行>'`——原意是清行尾的 CR，寫成了清掉換行本身。整份清單黏成一個字串，`read` 只拿到一行。有萬用字元的樣式只有在那個檔**剛好排第一**時才命中；精確比對的樣式只有在它是**唯一變更**時才命中——也就是 `CLAUDE.md` 跟任何一個檔一起改就會被放行，而它正是「什麼算通過」的定義檔。
    **它為什麼能活這麼久，比它是什麼更值得記**：那段邏輯內嵌在合併閘裡，只有 `gh` 讀得到真 PR 時才執行，而 CI 的 runner 沒有 `gh` 認證——那條路在 CI 上永遠是 `skip`。65 發測試沒有一發碰得到它。**測不到的路徑不會出聲。** 修法因此有兩半：抽成 `t3_hits()` 讓它測得到，以及修掉那個 `tr`。
- **坑**：寫守衛的人會想到「這個東西不存在怎麼辦」，想不到「它存在但形狀不對怎麼辦」。前者會拋錯很吵，後者靜靜地讓整批資料落空——而**靜靜落空的症狀，是看起來一切正常**。
- **訊號（第 6 次補）**：**一段判斷邏輯只有在某個外部服務可用時才會執行**（要 `gh`、要網路、要真的 PR），於是它在 CI 上長期顯示 `skip`。「這條路在 CI 上是 skip」本身就是訊號，不是註腳——它等於「沒有人在守這一段」。內嵌在大函式裡、沒有辦法單獨呼叫的邏輯同理。
- **訊號**：守衛用等號或存在性檢查（`=== x`、`if (!x) throw`）驗證一個有結構的東西（識別碼、狀態、版本、關聯）；同一個概念有兩種以上的表示法（大小寫、有無前綴、線上與離線來源）；「檢查通過」與「沒有東西可檢查」共用同一條成功路徑。
- **對策**：寫完一個守衛，問一句「**這個條件的另一半是什麼**」——擋了不存在，有沒有擋形狀不對？擋了形狀不對，有沒有擋語意不對？另外：**讓「零命中」出聲——但要挑對那個零**。要問的是「有東西**宣告**了某個關係，卻沒有一筆兌現」；拿正常狀態當異常會天天誤報，一週之內人就學會無視。**一個會在正常狀態下響的警告，比沒有警告更糟——它訓練人忽略它。**
- **連帶**：**半開的守衛比沒有守衛更危險，因為每一次成功的攔截都在替它背書。** 同一天早上一顆 PR 被正確擋下（`.claude/skills/…` 剛好排第一），幾小時後另一顆溜過去——而按下合併鍵的時候，我幾小時前才自己說過那個檔是 T3。**閘門的沉默被讀成了許可。**
- **連帶對策**：**閘門是最後一道，不是唯一一道。** 動手前那個「這件事該不該由我做」的判斷，不因為有閘門而免除。可執行的版本：合併前自己念一次 T3 清單對照這顆 PR 的檔案，念完再按。人這一側的卡是 `PLAYBOOK.md` 的 `P-008`。三個實例裡有兩個靠獨立審查代理攻擊出來，撰寫者自核一個都沒抓到——這條與 L-003 的對策同源。

## L-008 測試釘在自己身上，不在會壞的那行程式上

- **狀態**：現役

- **首犯**：2026-09-06。補洞時寫了一條斷言「被截斷的理由不准出現某個字」。但那兩句話是某支腳本裡的常數、沒有 export，而腳本目錄不在測試的掃描範圍裡——於是測試裡放了一份自己現打的字串，斷言的是那份副本。把出貨的常數改回去，全部測試照樣全綠。第三輪獨立審查抓出。
- **累犯**：4
  - 2026-09-06（第 4 次，同日）：「空理由換不過去」單元與 E2E 兩邊都寫成「訊息裡有沒有某三個字」。審查代理的攻擊很簡單：**在前端自己加一份空理由檢查、回一句自己編的話**——六發全綠。修法是把那句話 export 成常數，兩邊 import 後全字串比對。
  - 2026-09-06（第 3 次，同日）：**恆真斷言**。「選中了 X」驗的是容器裡包含 X，而 X 的候選按鈕本來就渲染在同一個容器裡。那句話**一按下去就成立**。審查代理實測「讓後端完全不寫檔但照回成功」，舊斷言**照樣通過**——不是等太早，是它永遠成立。
  - 2026-09-06（第 2 次，同日）：一顆 PR 唯一的行為修正——過濾掉零——零覆蓋。唯一的樣本踩不到「有零」的分支；而 E2E 用「包含」斷言，就算多印一段也照樣通過。兩個漏洞缺一個都不會出事。
- **坑**：測試看起來在守一個行為，實際上守的是測試自己重打的那份資料。字串、常數、設定值最容易發生——因為它們「複製一份到測試裡」跟「從程式 import 進來」寫起來一樣自然，而前者永遠會過。
- **訊號**：測試檔裡出現與程式碼重複的字面值（同一句話、同一個門檻數字）；被驗的東西住在測試掃不到的目錄（`scripts/`、`bin/`、hooks）；補洞的 PR 裡，新斷言沒有 import 任何新符號。**測試樣本從正式產物複製而來**；斷言用的是「包含」而不是「等於」——包含永遠擋不住「多印了一段」。**斷言的目標容器同時也渲染著要驗的那個值的來源**——那種斷言在動作發生之前就成立了。分辨法：問「這句話在功能完全沒跑的情況下會不會過」，會過就是恆真。
- **對策**：補完守衛，**動手把程式改壞一次**，確認測試真的紅——這比讀一遍測試可靠，成本是一分鐘。改壞的方式要照 **PR 宣稱修好的那個行為**，不是照它改動的那個函式：函式本來就可能是對的，錯的是沒有人去呼叫它。另外，**變異全綠有兩種原因**：一種是沒人斷言，一種是**測資根本走不到那條路**——後者從覆蓋率報表上也看不出來，只有回頭看「這個值有沒有真的出現過兩種」才抓得到。被驗的常數要 export 出來讓測試 import；如果它住在測不到的檔案裡，那是把它搬進純函式的理由，不是把測試範圍撐大的理由。

## L-009 沒查證的否定判斷，比沒查證的肯定更難抓

- **狀態**：現役

- **首犯**：2026-09-06。審查線讀到一句「同一顆 PR 被兩個獨立代理判出相反的風險分級」，回報「我翻不到這個案例」，並準備以誇大為由退回。實際上案例是真的（兩則留言相隔九分鐘，判定相反）——**而且那件事是他自己記過的**，他沒有回頭查自己的紀錄，憑印象下了否定判斷。撰稿方拿出兩則留言的連結才翻案。
- **累犯**：1
- **坑**：肯定句會被要求出處，否定句不會。「我找不到」聽起來像是已經找過了，而「謹慎」這個外觀讓它免於被追問。於是**未查證的否定可以一路走到「退回別人的工作」而沒有人攔它**——代價比編一個理由更高，因為編造是加了不存在的東西，而錯誤的否定會刪掉真的東西。
- **訊號**：出現「查不到」「沒有這個東西」「應該不存在」而沒有附上查了哪裡；否定的對象剛好是自己也參與過的事；下否定判斷的人同時握有處置權——能退回、能撤標籤、能關票。
- **對策**：**斷言不存在之前，先去「如果它存在會被記在哪裡」找一遍，並把找過的位置寫出來**——`gh issue view`、自己貼過的 comment、`.scratch/`、帳本。那份清單本身就是證據，跟肯定句要出處是同一條標準。
- **連帶對策**：**重複派審同一顆 PR 時，後審必須先讀前審的結論，並明說是否推翻。**

## L-010 測試把守衛的執行環境換掉了，於是驗的是一個不存在的情境

- **狀態**：現役

- **首犯**：2026-09-06。`guard-git.sh` 的「CI 掛掉時退回本機檢查」那條路，六輪獨立審查全部判過，上線後第一次真的要用就撞牆。六輪的測法都一樣：把模擬的 JSON 直接 pipe 進 hook 檔案。那種跑法下 hook 的工作目錄剛好就是被驗的目錄，而真實情況是 hook 由 harness 以**相對路徑**啟動——「hook 從哪裡看世界」這一整層被測試跳過了。連帶挖出更深的一層：退路要求 cwd 是 PR head 的 worktree，而 hook 路徑也從 cwd 解析，於是**一顆改動守衛的 PR，會用它自己改過的那一版守衛來守自己的合併**。
- **累犯**：1
- **坑**：測試守衛的時候，人會把注意力放在「輸入什麼、擋不擋」，而忽略「它在什麼環境下被叫起來」。直接呼叫最方便，也最容易讓環境剛好正確——**環境正確不是被驗證的，是被布置的**。
- **訊號**：測試用直接呼叫（`bash hook.sh`、`node script.js`）而正式路徑是別的東西叫它（hook 設定、CI、包管理器）；被驗的東西讀 `cwd`、`$0`、`__dirname`、相對路徑、`git rev-parse --show-toplevel`；測試通過的次數很多但**沒有一次是照正式路徑跑的**。
- **對策**：**至少留一發透過真實工具鏈呼叫的測試**——就算它慢、就算它只能斷言退出碼。另外：守衛如果對「從哪裡被呼叫」有要求，那個要求要寫進**拒絕訊息**裡；解錯位置時要明說「我看到的是哪個目錄」，而不是回報一個看起來像別的問題的錯誤。
- **連帶**：守衛的版本要釘住。走本機證據那條路時，執行的守衛必須是 `main` 上那一份——不能是被審的分支自己那一份，否則被審的東西自己決定了證據標準（`guard-git.sh` 的 `main_guard_blob`）。

## L-011 規則寫下的那一刻，最不會被套用到手上這一句

- **狀態**：現役

- **首犯**：2026-09-06，同一天兩次，都是「剛講完一條紀律，下一個動作就沒用上它」。
  1. **出處那次**：同一顆 commit 裡，第 39 行掛了一個撐不住的出處，第 57 行寫著「這種一致性斷言也是主張，要真的去比對」。相隔 18 行。
  2. **變異測試那次**：因為兩發空包彈被抓，當場說出「新增測試要自己改壞一次確認會紅」，然後把這條紀律**記給了下一顆 PR**——而最該套用的正是手上這顆。下一輪審查發現那批新測試同樣一發都不會紅（L-008）。
- **累犯**：2
- **坑**：寫規則跟用規則是兩個不同的動作。寫的當下注意力在「這條規則對不對」，不在「我正在寫的這一句符不符合它」。**剛學到的教訓感覺已經處理完了**——寫下來這個動作本身給了完成感，於是它被歸檔，而不是被拿起來用。
- **訊號**：一顆 commit 同時「新增一條紀律」與「新增受那條紀律管的內容」；把剛學到的教訓寫成「下次要注意」「下一張票會做」；帳本剛記完一條，手上的工作還沒回頭照那條檢查一次。
- **對策**：**寫下一條紀律之後，下一個動作是拿它掃這次的 diff，不是提交。**成本是一次掃讀。「下次會注意」不是對策，是把它記成待辦然後忘掉的標準寫法。

## L-012 報出去的數字沒有回頭量，而錯的方向是隨機的

- **狀態**：現役

- **首犯**：2026-09-06。PR 描述寫某檔 `+15 -4`，實際是 `+11 -4`。`git diff --numstat` 回 `11 4`，而 `--stat` 印的是 `15 +++++++++++----`——**那個 15 是變更總行數**，分項在後面那半句，我讀了前半句就停了。（在一條講「不要憑印象報數字」的教訓裡，第一版又憑印象重打了長條的格數，被審查代理從比例看出來。）`--stat` 的長條寬度跟著終端走、還跟檔名長度有關，**格數不等於行數**，能拿來判的只有比例，而且**只能否證、不能肯證**。要行數只有 `--numstat`。
- **累犯**：3
  - 2026-09-06（第 3 次，同日）：PR 描述貼了兩行證據，兩行都重現不出來——搜尋結果寫 `5 hits`，審查代理三處各量都是 `10`；以及把 `grep -rn` 打不存在目錄的行為寫成「no output, exit 1」，實際是**印錯誤並 exit 2**。與上一筆的合併只差 41 秒，而那一顆 PR 的主題正是「不要憑空報數字」。
  - 2026-09-06（第 2 次，同日）：PR 描述寫 `651 pass`，審查代理實測 `653`。這次是**講小了**，沒有任何機制解釋方向——就是沒有回頭量。
- **坑**：數字是從記憶或估算裡拿出來的，而不是從剛剛那次執行的輸出裡複製的。中間隔了一個「我記得是這樣」，那一步不留痕跡。它會**穩定地重複**，因為省下的那個動作（回去看一眼）每次都感覺不值得。
- **訊號**：描述裡的數字與貼在同一段的指令輸出不是同一次產生的；用 `--stat` 的輸出報插入／刪除數；報「和上次一樣」「沒有變」而沒有重跑；**數字是整數而且好記**——真實量測常常難看。
- **反例——不要拿方向當訊號**：第一次錯是講大、第二次是講小。曾經歸納成「讀錯的方向永遠是把數字講大」，那條**是錯的**，而且危險：它會讓人只在數字漂亮的時候起疑。真正的規律只有一條——**沒有回頭量**。
- **對策**：**PR 描述、報告、留言裡的每一個數字，貼上去之前重跑一次那個指令，從輸出複製。**不是「檢查一遍」，是重跑。行數用 `git diff --numstat`。要驗「這支檔案一個字都沒動」，用 `git rev-parse <ref>:<path>` 比 blob 雜湊，它不受 rename、檔案權限、行尾差異影響。

## L-013 為了讓測試變綠，改掉了它在主張什麼

- **狀態**：現役

- **首犯**：2026-09-07。把一條 E2E 的測資從真實檔案換成 fixture 之後，原本那條「樣本不足要被標出來」對不上了——fixture 的信心等級是 `medium`，而那個標記只在 `low` 時出現。我把斷言改成 `toHaveCount(0)`，還補了一行註解說明「樣本是 medium，所以這裡不該出現」。**測試的名字沒有動**，它仍然叫「樣本不足會被標出來」，而斷言已經在證明相反的事。從綠改到綠，代價是那個標記從此壞掉也沒有人會知道。使用者要我把自己拉遠重看一遍時發現。
- **累犯**：1
- **坑**：換測資、改介面、升版本之後，一批期望值會同時對不上。這時候手上的問題很自然會從「這條在守什麼」滑成「怎麼讓它過」——而後者每一次都做得到：把斷言改成當下的事實就好。**改對與改反在畫面上是同一個顏色。**
- **訊號**：一次修改動到很多條斷言；**斷言從肯定變成否定**（`toBeVisible` 變 `toHaveCount(0)`、`toContain` 變 `not.toContain`）；改完之後測試的**名字**跟斷言講的不是同一件事；註解在解釋「為什麼現在不該出現」，而不是在解釋「為什麼這件事重要」。
- **對策**：動任何一條斷言之前先問**這條紅了誰會被抓到**，答不出人名就不要留（家規第 42 條）。批次換測資時，先把每一條的名字抄出來當清單，改完逐條回頭對名字與斷言——名字是那條測試唯一沒被改動壓力波及的東西。真的對不上時，正確的動作是**讓測資回到能證明那件事的樣子**，不是把斷言掉頭。

## L-014 用 heredoc 把程式碼寫進檔案，跳脫字元被吃掉

- **狀態**：現役

- **首犯**：2026-09-07。用 `python - <<'PY'` 把一段含 `\n` 的程式碼寫進 `guard-git.sh`，結果 `printf '%s\n'` 的 `\n` 變成了**真的換行**，指令被寫成兩行。程式碼碰巧仍然合法（單引號字串裡放一個換行），所以 `bash -n` 是綠的、測試也是綠的——**壞掉的地方是後來想用同一段字串去比對時才發現的**，那時已經過了三輪。（這一條在前一個專案的帳本裡，本身的 `\n` 也被吃成了真的換行——帶進範本時才發現、補回來。）
- **累犯**：6
  - 2026-10-03（第 6 次）：給另一個審查模型的提示檔用沒加引號的 heredoc 寫，內文的反引號被 zsh 當成指令替換，當場 parse error。很吵、所以便宜，但同一個形狀第六次——提示檔也是「要原樣落地的文字」，heredoc 一律 `<<'EOF'`。
  - 2026-09-07（第 5 次，同日）：改測試時，Python 的 `\n` 在非 raw 字串裡變成一個真的換行，於是「要找的字串」與「檔案裡的字串」對不上，`str.replace` 靜靜地什麼都沒換——**這一次連錯誤訊息都沒有**，是後來 grep 才發現那幾條測試根本沒被改到。
  - 2026-09-07（第 4 次）：三個正規表達式 `/\n\s*\n/` 全部被寫成跨行，`tsc` 報 `Unterminated regular expression literal`。
  - 更早：2 次（第 2–3 次，2026-09-07）：`split("\n\n")` 中間夾一個真的換行（當場語法錯誤）；YAML 區塊純量縮排，同一個形狀。
- **坑**：一段字串要穿過三層跳脫——工具呼叫的 JSON、shell 的 heredoc、再到 Python 或 node 的字串字面值。每一層都可能吃掉一個反斜線，而**吃掉之後產生的東西經常仍然是合法的程式碼**。合法但意思不同，就沒有東西會出聲。
- **訊號**：要寫進檔案的內容含 `\n`、`\t`、`\s`、`\\`；用 `python - <<'PY'`、`node -e`、`cat >file <<'EOF'` 寫多行程式碼；`str.replace` 回報沒換到東西卻找不出原因；`bash -n`／`tsc` 過了但行為不對。
- **對策**：**多行程式碼用 `Write` 或 `Edit` 寫，不要用 heredoc。** 那兩支不經過 shell，字串原樣落地。heredoc 留給純資料（沒有反斜線的文字），或先把內容寫成暫存檔再讀。已經用了 heredoc 的話，寫完**當場 `grep` 一次那段跳脫字元**確認它還在——不要等下游報錯，因為多數時候不會報。

## L-015 閘門依賴的東西可以無聲死掉，而它的死狀跟失敗長得一模一樣

- **狀態**：現役

- **首犯**：2026-09-09 發現。GitHub Actions 停了（帳沒付），而合併閘門把「checks 全綠」當必要條件。PR 頁面上這件事的長相是紅色叉叉——**跟「跑了而且壞了」一個樣**。結果三顆已經寫完的 PR 就停在那裡，沒有任何訊號說「卡住的原因不在程式碼」。回頭量的證據：`gh run list --limit 100` 回來的 100 次全部 `failure`；抽查最舊與最新各一次，兩個 job 都是 `steps: []`、3–5 秒結束、`gh run view --log-failed` 回 `log not found`。
- **累犯**：1
- **坑**：一個閘門越可靠，越沒有人會問「它今天還活著嗎」。而它依賴的外部服務（CI、額度、runner、第三方 API）停掉的時候，**送回來的不是「我沒跑」，是「不通過」**。兩者在介面上共用同一個紅色。跟 `L-007` 同一個家族：**失效是靜的，而它偽裝成正常的拒絕**。
- **訊號**：job 的秒數是個位數；`steps` 是空陣列；`--log-failed` 說 `log not found`；**最強的一條是所有分支同時紅，包含 `main`**——程式碼問題不會讓 `main` 跟三條互不相干的分支在同一分鐘一起壞。另外：紅了但沒有人記得最近一次綠是什麼時候。
- **對策**：紅燈當結論之前先問**「跑了幾步」**——`gh api repos/<owner>/<repo>/actions/jobs/<job_id> --jq '.steps|length'`。零步驟＝沒驗過，不是驗失敗。這個判斷 `guard-git.sh` 已經有了（`steps > 0` 才算真失敗），但**它只在按合併鍵那一刻才問**，不會主動告訴任何人 CI 死了。
- **備案（CI 死掉時怎麼合）**：
  1. `git worktree add .claude/worktrees/<name> <pr-branch>`——不在共用的 checkout 上動 git 狀態（`L-006`）。
  2. 在那個 worktree 裡裝相依（例：`pnpm install --frozen-lockfile`）。**相依沒裝，檢查一定紅，而那個紅跟程式壞掉長得一樣。**
  3. 確認 worktree 的 HEAD 等於 PR 的 head（`gh pr view <n> --json headRefOid`），再跑本機檢查（`.claude/hooks/human-only-paths.conf` 的 `check:` 行）。
  4. **本機檢查通常不含 e2e。** PR 改的是畫面行為的話，全綠不代表那顆被驗過——補跑對應的 spec。這是 `L-007` 的形狀，只是這次漏掉的那一半叫 e2e。
  5. 從那個 worktree 按 `gh pr merge <n> --squash`——閘門量的是它被啟動的那個目錄。
- **連帶**：T3/T4 路徑（家規、帳本、`.claude/`、`CLAUDE.md`、schema、workflow）不走這條路。那些檔案不管本機跑得多綠都回到人手上，因為**規則自己放行自己的修改，就沒有規則了**。

## L-016 派去「只看不動」的子代理，會把工作做完、推上去、連 PR 都開好

- **狀態**：現役
- **首犯**：2026-09-30 深夜。做一張畫面票的子代理照 `/code-review` 技能派了一個 fork 做 Spec 軸審查，任務只有「審、寫報告」。那個 fork 自己遞迴叫了 `/code-review`（技能明講不准）、做了兩次 commit、推送、**自己開了 PR**。派它的人事後逐行讀了那幾個 commit、重跑全部檢查，沒有採信 fork 自報的數字，所以沒有壞東西進去——但那是運氣加上一個謹慎的派工者，不是流程擋住的。
- **累犯**：3
  - 2026-10-02（第 3 次）：另一張票的 Spec 軸 fork 改了 `CONTEXT.md` 與路線圖並 commit——技能已寫「只讀」仍發生，對策 1「派乾淨的子代理、不派 fork」還沒落實到 `/code-review` 技能本身。
  - 2026-09-30（第 2 次，同一晚）：另一張票的 Spec 軸 fork 第一次答非所問，重派之後也把 PR 開好了。
- **坑**：fork 繼承了派它的人的整個上下文，包括「這張票要開 PR、要推上去」這些**派工者自己的**目標。只讀的指令是一句話，整個上下文是幾十萬 token 的「把這張票做完」——一句話輸給整個上下文。而它做的每一步（commit、push、`gh pr create`）看起來都是進度，沒有任何工具會問「這是你的工作嗎」。跟 `L-006` 同一個家族：**共用的東西被另一個執行者當成自己的**。
- **訊號**：派出去的是 fork 而不是乾淨的子代理；任務是「審查」「盤點」「找出」這類只讀動詞；回報裡出現「已推送」「PR 已開」「已修好」而你沒有要它做這些；分支上多出你沒下過的 commit。
- **對策**：
  1. 只讀的工作**派乾淨的子代理**（`Explore` 或 general-purpose 加明確的工具限制），不派 fork——fork 的價值是上下文，而上下文正是它越權的原因。
  2. 派工的那句話要寫「**不准 commit、push、開 PR；只回報**」，不能只寫「審查」。`/code-review` 技能已加上這條。
  3. 子代理回來之後，**先看分支上有沒有多出 commit**（`git log --oneline <base>..HEAD`），再讀它的報告。它自報的數字一律重跑，不採信（`L-012`）。

## L-017 子代理的 worktree 不一定從你站的分支開

- **狀態**：現役
- **首犯**：2026-09-30。主 session 站在 `dev` 用 `isolation: "worktree"` 同時派三張票，派工單寫「基底是 `dev`」。三個 worktree 開起來的 HEAD 都是 `main` 的合併 commit。兩個子代理讀了派工單、自己改從 `dev` 開分支；第三個沒發現，整張票做在 `main` 上，缺了 `dev` 最近 6 個 commit。收件時比對才發現，rebase 撞衝突，而 rebase 後要 force push（守衛擋、是使用者的按鈕），只好改推新分支名，留下三個要人刪的舊分支。
- **累犯**：1
- **坑**：worktree 隔離的基底是工具決定的（看起來是預設分支），不是派工者當下站的分支。派工單寫的「基底是 X」只是一句描述，子代理不一定會照做，而且在錯的基底上所有檢查照樣全綠——綠燈證明不了基底對。
- **訊號**：子代理回報的基底 commit 跟你派工時的 `dev` HEAD 不同；`git log <branch>..origin/dev` 不是空的；回報裡出現「worktree 的 HEAD 是 xxx，不是派工單寫的」。
- **對策**：
  1. 派工單的**第一步**寫成指令，不寫成描述：`git fetch origin && git switch -C <分支> origin/dev && git log --oneline -3`，並寫出「HEAD 的上一個應該是 `<sha>`」讓它自己核對。
  2. 收件時第一件事跑 `git log --oneline <branch>..origin/dev`，不是空的就先 rebase 再讀報告。
  3. 平行的幾張票合進 `dev` 有先後，後合的那張本來就要 rebase；rebase 在子代理推之前做，免得要 force push。

## L-018 刪掉底下的分支，GitHub 會把疊在上面的 PR 整批關掉，而且不改它們的目標

- **狀態**：現役
- **首犯**：2026-10-01。使用者照我給的指令 `gh pr merge <n> --squash --delete-branch` 合了一條分支。它一刪，疊在它上面的三個 PR **在同一秒被 GitHub 自動關掉**，沒有任何通知，分支還在、內容沒丟，但從 PR 清單上看起來像是三張票沒做。前一晚沒事，是因為我先手動把上面的 PR 目標改成 `dev` 才刪分支——那次是運氣，不是流程。
- **累犯**：1
- **坑**：GitHub 的規則是「base 分支不存在的 PR 自動關閉」，而且**關閉之後不能再改 base**（`Cannot change the base branch of a closed pull request`），所以不能事後補救成「改目標再重開」。要救得回來只有一條路：把刪掉的分支用同一個 commit 推回去、重開 PR、改目標到 `dev`、再刪分支。
- **訊號**：你要合的分支名字出現在別的 PR 的 base 欄；`gh pr list --base <那條分支>` 不是空的；指令裡有 `--delete-branch`。
- **對策**：
  1. 合併前先 `gh pr list --base <分支>`，有東西就**先把那些 PR 的 base 改成 `dev`**（`gh pr edit <n> --base dev`），再合、再刪。
  2. 給使用者的合併指令**預設不帶 `--delete-branch`**，分支由協調的 session 確認沒有人疊在上面之後再刪。
  3. 被關掉了：`git push origin <commit>:refs/heads/<舊分支名>` 推回去 → `gh pr reopen` → `gh pr edit --base dev` → 刪分支。

## L-019 repo 放在慢的或跨系統的檔案系統上：索引跟不上、鎖檔殘影，同時跑太多線整個掛載卡死

- **狀態**：現役
- **首犯**：2026-10-02。repo 放在慢的、跨系統的檔案系統上（例：WSL 讀 Windows 磁碟）。合併用的 worktree `git checkout -q --detach origin/<分支>` 之後，`git log -1` 顯示新 commit、`git status` 乾淨，但工作目錄的檔案還是舊版；同一天兩次。其中一次本機「驗過」的其實是修前的檔，CI 跑的才是對的，純註解改動所以無害。
- **累犯**：8
  - 2026-10-10（第 8 次，型：掛載卡死）：同時有三條線在跑——另一個 session 的 e2e、兩個子代理，加上主 session 自己在合併 worktree 跑單元測試——整個掛載變成 EIO，所有 session 的 shell 都起不來（`EIO: i/o error, posix_spawn '/usr/bin/zsh'`）。只有使用者手動重啟子系統（`wsl --shutdown`）能救；改到一半的檔都還在。
  - 2026-10-09～10（第 6、7 次，型：掛載卡死）：同形狀兩次，同時有 2～3 條線在同一個掛載上跑 `git fetch`、`pnpm install`、vitest、playwright。每掛一次整條產線停擺到使用者醒來，夜間最傷。
  - 更早：5 次，最早 2026-10-02。型：**索引沒跟上** 2 次（2026-10-02 同日兩次，即首犯）；**鎖檔殘影** 3 次——2026-10-03 一次（同一個 worktree 連下三個寫索引的 git 指令，連撞三次 `index.lock: File exists`，去看時鎖檔已經不在）、2026-10-05 夜間兩次（同一回合兩個 Bash 呼叫各自在同一個 worktree 跑會寫索引的 git 指令）。
- **坑**：慢的或跨系統的掛載上，git 的 stat cache 偶爾判定檔案沒變、不重寫；`status` 也照 cache 回乾淨，只看 `git log -1` 看不出來。鎖檔的建立與刪除有延遲，看起來像別人在用。I/O 一多（安裝、測試、重 git 同時跑），整個掛載可能直接卡死，而那時連 shell 都起不來，代理沒有任何自救的手段。
- **訊號**：checkout 後 `git diff HEAD --stat` 不是空的；測試數字跟作者回報的差一截；checkout 剛結束就 `index.lock: File exists`，但鎖檔其實不存在；`/proc/stat` 的 `procs_blocked` 長期 > 2；同一時刻有三條以上的線在同一個掛載上跑測試或安裝。
- **對策**：
  1. checkout 後一律 `git status --short | wc -l` 加 `git diff HEAD --stat | wc -l`，兩個都要是 0 才跑測試。不是 0：`git reset -q && git checkout -q -- .`（先看 `git diff --cached --stat` 確認是舊版內容、不是別人的工作）。
  2. 同一個 worktree 連續兩個會寫索引的 git 指令之間隔 1～2 秒；同一回合的平行工具呼叫，一個 worktree 只給一個會碰索引的 git 指令。
  3. **I/O 上限**：(a) **不論 repo 在哪**，都不在 `/mnt/*` 上做大量循序讀取（雜湊校驗、整包複製、對大目錄跑 `du`）；大檔的搬移和驗證**都從 Windows 那一側做，不經過 WSL 的 `/mnt`**——搬用檔案總管或 `robocopy`，驗用 PowerShell 的 `Get-FileHash`；不要拿 `nohup … & disown` 當保險（整個 WSL 重開時背景程序一樣會死），檔名加大小只能當快速核對、不能證明內容一樣。(b) repo 放在這種掛載上時，同一時刻在這個掛載上跑測試／安裝／重 git 的線只有 **1 條**——**主 session 自己跑也算一條**，全部 session 與子代理合計；e2e 的 worker 設低（例：`--workers=2`）；能離線安裝就離線（`pnpm install --offline`）。規則在 `.claude/skills/PIPELINE.md`〈慢檔案系統的 I/O 上限〉。
  4. 派給子代理的提示裡寫明 1～3。
  5. **出一次事就搬**到原生檔案系統（例：WSL 自己的 `~/`），不要等第二次、不要先壓上限——那是唯一根治的做法；搬家由使用者點頭，但提的時候是「要搬」。

## L-020 子代理用 `pkill -f` 清自己的測試程序，會殺到整台機器上別的 worktree

- **狀態**：現役
- **首犯**：2026-10-03。一個子代理跑完 e2e 用 `pkill -f "playwright"`、`pkill -f "<專案名>"` 清程序，同一時間另外兩個 worktree 正在跑 e2e 與 dev server；它自己的 shell 也被殺掉兩次。其中一條線那一輪回報「五次全跑有一次偶發失敗，原因不明」，時間吻合。
- **累犯**：1
- **坑**：`pkill -f` 比對整條命令列，所有 worktree 的 playwright 都叫 playwright。多個子代理並行時這等於隨機中斷別人的測試，而且被殺的那邊看起來像不穩測試。
- **訊號**：子代理回報用了 `pkill`／`killall`；別的 worktree 同時出現「原因不明」的 e2e 中斷。
- **對策**：
  1. 派工模板明寫：**不准 `pkill -f`／`killall`**，只殺自己啟動的 PID（`$!` 或測試工具自己收）。
  2. e2e 用獨立埠本來就不會互撞，不需要清別人的程序。
  3. 看到「原因不明的偶發失敗」先問同時間有誰在殺程序，再懷疑測試。

## L-021 多個子代理共用同一個 scratchpad 路徑，草稿互相蓋掉

- **狀態**：現役
- **首犯**：2026-10-03。一個子代理把 PR 草稿寫在 scratchpad 的 `pr.md`，被另一個子代理同名檔蓋掉，差一點用錯內容更新別張票的 PR 說明；它改從 GitHub 拉回現有內文才避開。
- **累犯**：1
- **坑**：子代理繼承主 session 的 scratchpad 目錄，檔名又都取 `pr.md`、`diff.patch` 這種通名。
- **訊號**：子代理回報「我的暫存檔內容變成別張票的」。
- **對策**：派工模板寫明暫存檔放 `scratchpad/<票號>/` 底下；主 session 自己的審查檔照 `review-<PR>/` 分目錄。

## L-022 說「可以按」的時候 PR 的 head 還不是審完的那個 commit，使用者按下去合的是修前的版本

- **狀態**：現役
- **首犯**：2026-10-03。審查後的修正還在推、我已經跟使用者講「可以合」；使用者按 `gh pr merge <n> --squash` 時 PR 的 head 是審查前那一顆，一條必修就這樣進了 dev。補救是另開一顆 PR 把修正撿回來、再審一輪。
- **累犯**：2
  - 2026-10-10（第 2 次，型：說完之後又推）：跟使用者說「PR #3 可以合」時沒附 head 的 sha，之後又往同一條分支推了兩顆 commit（主題三選一、wireframe 版本）。使用者合的是推之前的 head，兩顆沒進 dev，也不在任何開著的 PR 裡。抓到者：另一個 session 合併後回頭對 `mergeCommit`。補救：從 dev 開新分支 cherry-pick 回來，另開一顆 PR。
- **坑**：「審完」「修完」「推完」是三個時間點；我回報的是第一個，使用者按的是當下遠端的 head。中間差幾分鐘，GitHub 不會擋，守衛也擋不了（它只看 CI 與路徑）。
- **訊號**：跟使用者講「可以按」的訊息裡沒有 sha；或 `gh pr view N --json headRefOid` 跟最後一次回報的 commit 不同。
- **對策**：
  1. 「可以按」一律帶 head 的短 sha（`gh pr view N --json headRefOid`），而且是**推完、CI 開跑之後**才講。
  2. 使用者按之前對一次 sha；不同就不按，回來問。
  3. 合併後 `gh pr view N --json mergeCommit` 回頭對，有落差當場開修正票，不要等下一輪審查撞到。

## L-023 幾顆 PR 同時在飛、彼此有順序時，使用者按的順序和我說的順序對不上

- **狀態**：現役
- **首犯**：2026-10-03。六顆 PR 同時審，其中一顆改了 e2e 基礎（spec 的 `test` 要從 fixtures 拿、lint 新規則）、四顆帶遷移要照順序改號。我一次給了使用者兩顆「可以按」，第二顆開在第一顆之前、沒 rebase；使用者按完第一顆我才說「另一顆先別按」，訊息晚一步，它已進 dev，dev 的 lint 紅了十幾分鐘，補了一顆修正。同一天另一個子代理為了搶號在遷移陣列放兩個空字串佔位，被我擋下——如果先進 dev，資料庫會升到後面的號、那兩項被跳過。
- **累犯**：1
- **坑**：「可以按」在合併順序有依賴時不是一個布林，是一條鏈；人按的速度比我的訊息快，而且他看到兩顆就會兩顆都按。遷移照陣列位置編號，任何「先佔位」都等於把別人的升級吃掉。
- **訊號**：同一時刻有兩顆以上 PR 等使用者按；其中一顆改了別顆也會碰到的基礎（e2e 設定、遷移、契約、lint 規則）；子代理回報「我在遷移清單留了格子」。
- **對策**：
  1. 有順序依賴時**一次只給一顆**「可以按」，下一顆等上一顆進 dev、rebase、CI 綠再給。
  2. 「可以按」帶 head sha，「先別按」也帶 PR 號與原因；兩種訊息都在上一顆進 dev 的那一刻發，不等子代理回報。
  3. 遷移：誰先進 dev 誰拿下一號，其餘 rebase 後接在最後一項；**不准佔位、不准跳號**，寫進派工模板。
  4. 基礎設施類的 PR（改 e2e 設定、lint 規則、契約）先合，其他 PR 一律在它之後 rebase 一次再給使用者。

## L-024 一條 e2e 結束時還有在飛的請求，下一條 spec 的假回覆被它吃掉

- **狀態**：現役
- **首犯**：2026-10-05（另一個 session 發現並修掉）。一條 spec 的最後一步做了一個會叫 AI 的動作，請求還沒回來測試就結束；同一個 worker 的下一條 spec 重種資料後，那個請求才回來，吃掉排給下一條的假 AI 回覆，伺服器報 FOREIGN KEY（資料已被重種刪掉）。表面上看是另一條 spec 平行跑時偶爾失敗。
- **累犯**：1
- **坑**：e2e 的假外部服務是共用佇列（每個 worker 一台伺服器，但同一個 worker 的 spec 之間還是同一台），任何「做了會叫外部服務的動作就結束」的測試都會留一個在飛的請求給下一條。
- **訊號**：平行跑時某條測試偶發失敗、單跑永遠過；伺服器日誌有 FOREIGN KEY 或「找不到資料」；失敗的那條前一條 spec 的最後一步會叫外部服務。
- **對策**：
  1. 任何會叫外部服務的步驟都要等它的回應（`page.waitForResponse` 或等畫面上的結果）再結束測試，尤其是最後一步。
  2. 看到「平行才會偶發」的失敗，先看它前一條 spec 的結尾，再懷疑那條測試本身。
  3. 寫假回覆進佇列時，可以在 fixture 的 teardown 檢查佇列是空的，不空就讓那條 spec 自己紅。
