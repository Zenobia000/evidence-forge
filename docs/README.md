# docs/ 的地圖

分層的問題只有一個：**這句話多久會變一次？**

| 層 | 回答什麼 | 變動頻率 | 放什麼（例） |
| --- | --- | --- | --- |
| `00-intent/` | **為什麼做**、什麼算好 | 極低 | 核心價值、在解什麼問題、給誰用、要驗證的假設、路線圖 |
| `10-truth/` | **什麼必須成立**：產品需求、能力、設計契約、決策 | 低～中 | PRD、架構、設計系統與介面契約、測試藍圖、UAT 案例、`adr/` |
| `20-state/` | **現在做到哪** | 高，每顆 PR | 進度表、待辦對照（引用需求編號） |
| `30-snapshot/` | **當時是什麼** | append-only | 研究、排程計畫原文、盤點、鞏固站紀錄 |
| `history/` | 這套工作流是怎麼長出來的 | 不再變 | 範本的來歷長文 |
| `agents/` | 給技能讀的組態 | 換工具時才變 | 議題追蹤器、領域文件位置、接力（選用） |
| `templates/` | 外來的文件範本，只抄結構 | 換範本時才變 | VibeCoding 範本（來源與規則見 `templates/README.md`） |

編號是**優先序**：`00 → 10 → 20 → 30`。意圖決定事實，事實決定該有什麼狀態，
狀態沉澱成快照。反過來不成立——快照永遠不能回頭覆蓋事實。

## 四條治理規則

1. **意圖不記進度。** `00-intent/` 裡出現「目前完成 8 條」就是寫錯地方了。
2. **事實不記 TODO。** `10-truth/` 說「必須成立什麼」，不說「還沒做」。
3. **狀態不定義規格。** `20-state/` 只引用需求編號，不解釋需求是什麼。
4. **快照不回寫歷史。** 那一天判定某條未完成，之後做完了也不改那份紀錄。

第 2 條是分層的主因：前一個專案的需求文件曾經有 116 處「已達成／未達成」，
每合併一顆 PR 就得改它——**每一次進度更新看起來都像規格變更**。

## 一件事只有一個家

每一類東西只住一個地方，其他地方只能引用。新專案長出新的一類東西時，先在這張表加一列，再開檔。

| 東西 | 唯一的家 | 其他地方只能 |
| --- | --- | --- |
| **票**（一張要做的事） | GitHub issue | 引用票號 |
| **這一輪做什麼**（範圍、P0／P1／P2） | GitHub issue | 引用 issue 編號 |
| **決策**（難以回頭、影響未來選擇） | `10-truth/adr/`，一決策一檔 | **引用 ADR 編號，不重述理由** |
| **產品需求**（誰、為何、核心體驗、MVP） | `10-truth/requirements/prd.md` | 引用章節與需求編號 |
| **BDD 情境**（Gherkin，一個 Epic 一檔） | `10-truth/requirements/features/` | 引用檔名與 Scenario 名稱 |
| **架構**（元件、資料模型、API） | `10-truth/architecture.md` | 引用章節 |
| **介面不能違反什麼**、設計 token | `10-truth/design/` | 引用 token 名稱，不抄值 |
| **測試層、接縫、各層時間上限** | `10-truth/test-blueprint.md` | 引用 ID |
| **UAT 案例** | `10-truth/uat-cases.md` | 引用案例編號 |
| **核心價值、一條需求該不該做** | `00-intent/` | 引用 |
| **路線圖**（階段、每階段的門） | `00-intent/roadmap.md` | 引用階段編號，不另寫一版 |
| **領域語言** | 根目錄 `CONTEXT.md` | 引用詞條 |
| **工作方法**（家規、帳本、路由） | `Ai-coding-principle/` | 引用條號 |
| **開發流程的順序與停點** | `.claude/skills/PIPELINE.md` | 引用節名 |
| **狀態** | `20-state/`（第一張票開工時決定檔名） | 引用 |
| **文件範本**（外來的、不改內文） | `templates/` | 抄結構；專案內容不寫在那裡 |

**架構跟實作它的程式一起進來。** 程式還沒有的時候先寫架構，等於在 `10-truth/` 記 TODO（第 2 條）。
規劃階段的元件、資料欄位、API 草案先留在 `30-snapshot/plans/` 的原文裡，只是參考；
哪一段做出來，就跟那段程式一起寫進 `architecture.md`。架構的章節標題直接標出它實作哪些需求編號，
例如「匯出（需求：FR-EXP-001、FR-EXP-002）」，不另外維護對照表。

**什麼進 ADR：** 換掉它要付出代價的決定。只影響這一輪的範圍取捨留在
那一輪的 issue 或 PR 裡，不進 ADR——ADR 長到三十份而其中二十份不再有人在乎時，
它就不再是可信的決策史。

## ADR

編號從 `0001` 起，四位數，一決策一檔：`10-truth/adr/0001-<短名>.md`。

**ADR 有時間順序，後面的可以覆蓋前面的。** 兩份說法不同時，以編號大的為準。
被覆蓋的那份不改內文，只在標頭補一行「後續修正：由 ADR-XXXX 修正」，指向新的那份——
舊的理由還在，讀的人也知道要往後看。

**編號不重用。** 拿掉一批 ADR（例如整個系統重寫）之後，新的從下一個號接著編。舊的 issue 和 PR 還指著那些編號，
重用之後，舊連結會指到一份內容完全不同的決定，比指不到還糟。要沿用舊決定，**重寫一份新的，不要把舊檔案複製回來**——
複製回來的 ADR 會帶著舊系統的舉例，而那些例子已經指不到任何東西。

## 上游技能寫死的路徑

vendored 技能不手改（`.claude/skills/VENDOR.md`），所以下面這幾支預設寫的位置跟本 repo 不同，
跑完把輸出放到右欄。左欄刻意不用反引號，因為那些路徑在本 repo 不存在。

| 技能 | 它預設寫的位置 | 本 repo 的位置 |
| --- | --- | --- |
| `/to-architecture` | docs/03_architecture_design.md | 10-truth/architecture.md，跟程式一起進 |
| `/to-architecture`、`/implement`、`/frontend-spec` | docs/capabilities/<name>.md | 不設這一層；架構章節標題直接標需求編號 |

| `/test-blueprint` | docs/test-blueprint.md | 10-truth/test-blueprint.md |
| `/uat-cases`、`/browser-evidence` | docs/uat-cases.md、docs/uat/ | 10-truth/uat-cases.md；證據目錄 10-truth/uat/ |
