# ADR-0021：對話鑰匙 `conv:<對話 id>:<第幾次開>`，對話只碰得到自己開的工單

> **狀態：** 提案（#80 spike 起草，等專案擁有者拍板） | **日期：** 2026-10-13 | **決策者：** 專案擁有者
> 依 `docs/templates/vibecoding/04_architecture_decision_record_template.md` 撰寫。
> **補充 ADR-0011 §3.6**（工單身分）與 **ADR-0019 §4**（對話要另外定義鑰匙與範圍）。
> spike 的程式在分支 `spike/p2-pi-rpc-chat`，結論在 #80 的留言。

## 1. 背景與問題

- **上下文：** 改成聊天室之後（ADR-0019），每個對話是一個長時間開著的 Pi（RPC 模式）。它也要打模型、要開工、要讀報告，所以閘道要認得它、替它記帳、限制它能碰什麼。
- **工單鑰匙不能直接拿來用：** 工單鑰匙 `job:<工單>:<段>:<次>` 只在一段一次的 Pi 活著時有效，閘道照它找工單資料夾、記帳、算能寫哪裡。對話沒有段、沒有次，而且會被殺掉再接回、會跨好幾張工單。
- **要回答三件事：** 對話拿什麼鑰匙；它的帳記在哪、預算怎麼算；它能碰哪些檔。
- **為什麼要寫成 ADR：** 這是閘道的身分與範圍規則（T3），之後所有對話工具都照它判斷；改回來要動閘道、帳本格式與 ef-tools。

## 2. 考量的選項

| 選項 | 結果 |
| :--- | :--- |
| 對話借用一張假工單的鑰匙（例：`job:c-xxx:chat:1`，對話資料夾放在 `jobs/` 底下） | 不採用：對話不是工單（`CONTEXT.md`），放在 `jobs/` 會被執行器、看板、帳單當成工單；`job.md` 的狀態機也套不上 |
| 對話不經閘道，主機直接替它打 Anthropic | 不採用：違反「閘道是唯一會花錢、會對外連線的地方」（ADR-0011 §3.4），對話的花費也不會進帳本 |
| **新的一種鑰匙 `conv:<對話 id>:<第幾次開>`，跟工單鑰匙用同一張登記表** | **採用** |

## 3. 決策

1. **鑰匙格式：`conv:<對話 id>:<第幾次開>`。**
   - 主機每替這個對話開一次 Pi，次數加一，記在 `conversation.json` 的 `launches`。
   - Pi 活著時登記在閘道（跟工單鑰匙同一張登記表），Pi 結束就撤銷。
   - 接回之後只認最新那一把：前一個還沒死透的 Pi 拿舊鑰匙來，一律拒絕（跟工單鑰匙「重跑同一段同一次」的道理一樣）。
   - 對話 id 的字元規則跟工單 id 一樣（英數字開頭，只准英數字、點、底線、連字號），因為它會拿來拼路徑。
2. **對話資料夾放在 `$EF_DATA/conversations/<對話 id>/`：**
   - `conversation.json`：標題、建立時間、預算、開過幾次。只有主機寫。
   - `jobs.jsonl`：這個對話開過的工單，一行一張。只有閘道寫，只增不改。
   - `ledger.jsonl`：對話本身的模型呼叫。只有閘道寫，只增不改。
   - `pi-session/`：Pi 的對話紀錄（`--session-dir`，session id 就是對話 id）。只有 Pi 寫。
   - 工單仍在 `jobs/<工單 id>/`，不搬進對話資料夾：執行器、帳單、既有工具都不用改。
3. **帳記在對話自己的帳本，算進每月總額。**
   - 閘道內部用 `conv:<對話 id>` 當擁有者 id（帶冒號，不可能跟工單 id 撞），帳本那一行的段是 `chat`、次是第幾次開。
   - 每月上限的加總包含所有對話的帳本。
   - 對話另有自己的美元上限（`conversation.json` 的 `budget_usd`，預設 US$1），只管對話本身的呼叫；它開的工單各自用工單的預算。
4. **能碰的範圍：**
   - 對話鑰匙只能用對話的工具：`analyze`、`read_report`、`job_status`（之後加 `rewrite`、`read_article`、`list_personas`）。讀寫檔、抓網頁、搜尋、跑腳本這些段的工具一律拒絕。ef-tools 也只對對話註冊對話的工具，模型根本看不到段的工具。
   - 段的鑰匙不能用對話的工具（段不能自己開新工單）。
   - 讀報告、問狀態只准讀列在這個對話 `jobs.jsonl` 裡的工單；別的對話開的一律拒絕，而且不說那張單存不存在。
   - 對話沒有任何寫檔工具：報告與文章只能由它開出去的工單產生（chat.feature「對話的 agent 不自己寫內容」）。
5. **工單跑完怎麼回到對話：** 主機看到這個對話的工單結束，就對它的 Pi 送 `/ef-job-done <工單 id>`（ef-tools 的指令，不是模型能叫的工具）。ef-tools 用對話鑰匙問閘道那張單的狀態，在對話紀錄裡放一則 `ef-job` 通知，叫模型接著讀報告。同一張單已經通知過就不再通知，所以主機在每次接回時可以把跑完的單全部再送一次。

## 4. 後果

- **正面：**
  - 閘道的模型轉送、預留與結算、快取、帳本都不用分兩套，對話跟工單走同一條路。
  - 對話的花費進帳本，每月總表算得到（chat.feature「對話本身的花費也入帳」）。
  - 範圍規則全部在閘道一個地方判斷，ef-tools 只轉送。
- **負面：**
  - 帳本那一行的 `job_id` 欄位會出現 `conv:<對話 id>`。帳單要把它當成「對話」顯示，不是當成一張工單；之後想分清楚可以加一欄，那是帳本格式的改動（T3）。
  - 環境變數仍叫 `EF_JOB_KEY`，裝的卻可能是對話鑰匙；名字不準，但改名要同時改 ef-tools 與執行器。
  - 每個打開的對話都是一個常駐的 Node 程序（spike 量到常駐記憶體約 115 MB），要有閒置多久就關掉的規則。
- **還沒決定、要擁有者拍板的：**
  - **同一份素材跨對話共用分析？** 開單沿用「同一份素材、同樣的目標已有工單就拿回那一張」，所以兩個對話丟同一篇文章會拿到同一張工單，兩個對話都讀得到它的報告。spike 照這樣做；這對知識庫是好事，但如果要「每個對話只看到自己的」，就要把對話 id 放進去重的鍵。
  - 對話預算用完時，對話裡要怎麼說、要不要讓創作者在 UI 上加額度。
- **影響範圍：** `src/evidence_forge/gateway/`（鑰匙、範圍、預算、帳本路徑）、`harness/pi/extensions/ef-tools/`、`paths.py`、帳單頁、`CONTEXT.md`（新增「對話鑰匙」一列，「工單鑰匙」補一句反例）。
- **重新評估觸發：** 一個對話要同時開很多個 Pi（例如分頁各一個）；或對話要能直接用某個段的工具（例如自己抓網頁）。
