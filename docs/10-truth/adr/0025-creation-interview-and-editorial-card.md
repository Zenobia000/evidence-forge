# ADR-0025：寫稿前先訪談，每一關給選項；決定記成只增不改的事件，編輯卡由事件算出來

> **狀態：** 已接受（創作者 2026-10-15 拍板；PR 合併即生效） | **日期：** 2026-10-15 | **決策者：** 專案擁有者
> 依 `docs/templates/vibecoding/04_architecture_decision_record_template.md` 撰寫。
> **修正：** ADR-0019 §3.2（分析完不是直接重構，而是進訪談；寫稿只讀訪談收斂出來的編輯卡）；ADR-0020 §3.3、§3.4（重構的輸入改成編輯卡快照；稿後多幾條機械能查的程式檢查，仍不用模型檢查內容）。
> 規劃原文：`30-snapshot/plans/2026-10-15-content-workflow-integration.md`。票：#105。

## 1. 背景與問題

- **上下文：** 照 ADR-0019，創作者看完分析報告說「寫第 N 個」，系統就用指定的角色與文體一次寫完一篇。觀點、例子、主幹、標題全由模型挑，創作者只能事後帶一句意見再改。
- **創作者自己的寫作流程**（Sunny 內容流程，32 篇實戰）走的是另一種分工：作者在每一站拍板，順序是文體 → 核心觀點 → 只有作者能給的例子 → 邊界 → 工作標題 → 主幹 → 第一人稱與配圖；AI 負責列候選、整理、寫初稿與產圖。整篇的狀態寫在一份一直改的編輯卡（`brief.md`）。它自己的交接文件寫明缺一個「有狀態的工作流程引擎」：關卡現在全靠對話維持，選過什麼沒有紀錄，「作者沒給實測資料就不動筆」這類規則也沒有程式擋。
- **創作者要的體驗（2026-10-15）：** AI 有條理地訪談，每一步給選項讓他挑或補充；看得到自己選了什麼、沒選什麼、最後的結構與選題；每篇的素材與圖片都留著可以再調。
- **為什麼要寫成 ADR：** 這改了人在流程裡的位置（從「看完報告就交給模型寫」變成「每一關拍板」）、多了一種狀態（編輯卡與決策紀錄），也改了重構的輸入與稿後檢查的範圍；後面八張票都照這份做。

## 2. 考量的選項

| 選項 | 結果 |
| :--- | :--- |
| 維持一次寫完，只把目標（`goal`）寫得更細 | 不採用：創作者的選擇沒有留下來，也沒辦法回頭只改一關 |
| 做一張固定欄位的表單（照編輯卡範本填） | 不採用：ADR-0019 否決過固定表單；而且創作者要的是 AI 先給幾個有理由的選項，不是空白欄位 |
| 編輯卡是一個一直覆寫的檔（照搬現在的 `brief.md`） | 不採用：看不到過程；跟 ADR-0010「只增不改」衝突，寫稿工單也說不清楚當時讀的是哪一版 |
| **在聊天室裡一關一關訪談；每個決定記成只增不改的事件，編輯卡由事件算出來；寫稿工單帶一份當時的快照** | **採用** |

## 3. 決策

### 3.1 三種起點

訪談可以從三個地方開始，都在同一個對話裡：

1. **報告的第 N 個題材。** 創作者在分析完之後說「寫第 N 個」。那個題材的暫定標題、角度與建議文體帶進第 1 關當預設選項。
2. **創作者自己的一個想法。** 一句話就可以開始，沒有分析報告。
3. **貼素材。** 創作者自己的筆記、數據、草稿或口述的逐字稿，當成這張編輯卡的素材，不當成別人的文章去分析。要拿別人的文章當起點，照舊走分析（ADR-0019），再從報告的題材開始。

### 3.2 六個訪談關卡

順序固定，一次只問一關，這一關有決定才往下：

| 關 | 問什麼 | 記下來的是 |
| :--- | :--- | :--- |
| 1 文體＋主題 | 這篇的主證據是什麼、讀者讀完要做哪個決定 | 一個文體、一個主題（ADR-0026） |
| 2 核心觀點 | 把感覺命名成一個說得出口的觀點 | 觀點的名字與一句話 |
| 3 只有作者能給的例子 | 作者自己遇過、做過、量過的東西 | 作者給的例子與實測資料 |
| 4 邊界 | 這個觀點在什麼條件下成立、什麼情況下不成立 | 成立條件與失效條件 |
| 5 工作標題 | 3～5 個候選標題 | 一個當錨的工作標題（正式標題寫完再訂） |
| 6 框架、主幹與圖文分鏡 | 用哪種結構、各節的順序與主張、每節要不要配圖、配哪一種 | 框架、大綱、圖文分鏡，以及文章會提出的主張清單 |

- **每一關：** 對話的 agent 列 3～5 個選項，每個附一句理由；創作者點一個，或自己打字補充、改寫。創作者口述的內容先整理成條列，請他確認再記。
- **第 3 關不准替作者編經歷。** 這一關的選項只能是提示（「你有沒有遇過……」），內容一定來自創作者。文體是 `product-case` 或 `benchmark`、而創作者沒有給實測資料時，停在這一關：請他補，或回第 1 關換文體。這是原本流程裡「第一人稱確認」的那一步。
- **第 6 關列出文章會提出的主張，每條附「怎麼會被證明是錯的」，給創作者看過。** 原本流程在寫完之後逐句做可否證測試；這裡改成寫之前在主張層級看，因為稿後不用模型檢查內容（ADR-0020，§3.6）。
- **創作者說「你幫我選」：** agent 照樣記一筆決定，選它排第一的選項，補充寫「交給 AI 選」。每一關都有一筆看得到的決定，沒有例外的路。
- 原本流程的第 7 站「配圖」併進第 6 關的圖文分鏡；產圖本身是寫稿之後的配圖工單（ADR-0027）。

### 3.3 決策紀錄與編輯卡

- **位置：** `$EF_DATA/conversations/<對話 id>/cards/<卡 id>/`。一個對話可以有好幾張卡（同一份報告挑了兩個題材，就是兩張）。
- **決策紀錄 `decisions.jsonl`：** 一行一個事件，只增不改，只有閘道寫（經對話的工具）。事件有兩種：
  - 提出選項：哪一關、問題、選項（每個有名稱與理由）、可不可以自己寫、時間。
  - 做了決定：哪一關、選了哪個選項或創作者自己寫的文字、補充、時間。
- **編輯卡 `card.json`：** 由事件從頭算一次得到的當前狀態：每一關現在的決定、還沒決定的關、要重確認的關。它只是快取，可以隨時重算；兩邊對不上時以事件為準。壞掉的一行跳過，不拖垮整張卡（跟帳本的讀法一樣）。
- **回頭改一關：** 記一筆新的決定事件。後面已經決定過的關卡在編輯卡上標「要重確認」，原本的決定留著當預設；創作者確認（再記一筆決定，內容可以一樣）或改掉之後才取消標記。
- **對話的工具**（範圍照 ADR-0021：只碰得到這個對話自己的卡）：
  - `propose_options(station, question, options[{label, why}], allow_other)`：記下提出的選項，交給畫面畫成按鈕。不打模型、不花錢。
  - `record_decision(station, choice, note)`：記下決定。
  - `read_card`：讀編輯卡。
- **寫稿要六關都有決定、而且沒有要重確認的關。** 還有空的或要重確認的，寫稿工具拒絕，訊息說是哪幾關。

### 3.4 寫稿工單帶一份編輯卡快照

- 開寫稿工單時，閘道把當下的 `card.json` 複製進工單的 `input/`。工單只讀這份快照，不讀活的編輯卡；之後再改編輯卡不影響已經開出去的單。
- 改稿、或改了編輯卡再寫，都是新工單、新快照（ADR-0019 §3.6 的「每一版都是一張新工單」照舊）。
- 寫稿工單的輸入：編輯卡快照＋分析報告與來源（從報告的題材開始時才有）＋角色資料（ADR-0026）。從報告開始時，「不讀原文全文」「內文不提原文與原作者」「參考來源第一條是原文」照舊（ADR-0020、ADR-0024）；從自己的想法或素材開始時沒有原文，這幾條不適用。

### 3.5 對 ADR-0019 的修正

- 分析報告之後，「寫第 N 個」開始的是訪談，不是直接重構；訪談收斂成編輯卡，寫稿才開工。
- ADR-0019 的「分析完直接寫」照樣可以說，但意思變成「每一關你幫我選」：六關照樣各記一筆決定（§3.2），創作者事後在決策紀錄裡看得到 AI 替他選了什麼。
- 分析與重構仍是兩件照配方跑的工作；訪談在對話裡，不是工單，也不照配方跑。

### 3.6 對 ADR-0020 的修正：稿後只多查機械能查的

ADR-0020 的「稿後不用模型檢查內容」不變。程式檢查多這幾條，全部只用程式判斷：

- 文章的 front matter 齊全（`title`、`description`、`genre`、`theme`）。
- 有參考資料一節，每一筆有網址。
- 圖文分鏡裡的每一張圖在文章裡都留了圖位。
- 圖文節奏（配圖工單，ADR-0027）：第一張圖之前、兩張圖之間的字數照規則。
- 數據圖的證據鏈（配圖工單，ADR-0027）：每個數字對得回證據帳本。
- 句型這類寫作規則屬於角色的聲音（ADR-0026），規則內容不寫進 repo。程式檢查可以照角色資料裡列出的句型去擋，清單在角色資料、檢查的程式在 repo。

## 4. 後果

- **正面：**
  - 創作者在寫之前就拍板觀點、例子與主幹，寫出來的東西是他的，不是模型挑的方向。
  - 每一個選過、沒選的方向都留在決策紀錄裡；回頭只改一關，後面的關卡自動標出要重看。
  - 寫稿工單只讀一份凍結的快照，重跑、比對版本都說得清楚當時依據的是什麼。
  - 交接文件說缺的「有狀態的流程引擎」，用現有的對話、閘道、只增不改的檔就做得出來，不另外架資料庫。
- **負面：**
  - 從報告到文章多了六關來回，對話的模型呼叫變多（每關約一到兩輪，`fast`）。
  - 對話的工具從只讀變成會寫檔（決策紀錄）；寫入只經閘道、只寫進這個對話的資料夾，範圍檢查要跟著加。
  - 「要重確認」讓回頭改一關之後要多點幾下；這是刻意的，後面的決定可能是照前面那一關推出來的。
  - 第 6 關的主張清單是寫之前的承諾，寫稿時模型仍可能多寫出清單外的說法；稿後不用模型檢查，只能靠創作者讀稿。
- **影響範圍：** `src/evidence_forge/gateway/chat_tools.py`、`conversations.py`、`chat/`（對話主機推選項給畫面）、`harness/pi/extensions/ef-tools/`、`harness/pi/chat-system-prompt.md`（訪談規則）、`harness/recipes/rewrite.md` 與 `harness/skills/rewrite/`、`runner/stage_inputs.py`、`checks/article.py`、`ui/`（選項按鈕、決策分頁）；PRD §2、§3、§4、§5、§7；`CONTEXT.md`。
- **重新評估觸發：** 創作者常常每關都說「你幫我選」（訪談變成負擔）；或常常寫到一半才發現某一關的決定行不通（關卡的順序或內容要改）。
