# ADR-0026：文體換成 7 種、多一個主題欄；角色資料夾每個角色同一種樣子

> **狀態：** 已接受（創作者 2026-10-15 拍板；PR 合併即生效） | **日期：** 2026-10-15 | **決策者：** 專案擁有者
> 依 `docs/templates/vibecoding/04_architecture_decision_record_template.md` 撰寫。
> **取代：** ADR-0015 §3.1 的 12 種文類清單。**修正：** ADR-0015 §3.2 的作家設定（角色資料夾多了 `craft/`、`themes.md`、`lessons.md`、`brand.yaml`，文體風格檔多寫價值與 CTA）。ADR-0015 的組合方式（文體定義 × 角色）、未校準、開段時複製進 `input/` 都不變；ADR-0024「骨架是思考的順序，不當標題」照舊適用於新的 7 種。
> 規劃原文：`30-snapshot/plans/2026-10-15-content-workflow-integration.md`。票：#105。

## 1. 背景與問題

- **上下文：** ADR-0015 定了 12 種文類，依「讀者讀完得到什麼」分組，每種只有辨識訊號、抽取欄位與骨架。改成聊天室之後，重構從分析報告出發（ADR-0020），抽取欄位已經用不到；文類實際上只剩骨架。
- **創作者自己的寫作流程**用的是 7 種文體，經過 32 篇實戰：每一種除了一句話的定義，還定了主證據（這種文章靠哪一種證據撐起來）、必要內容、搜尋策略、推薦的結構公式，另有一個主題欄記這篇是從哪個選題方向來的，用來看內容有沒有偏食。
- **創作者 2026-10-15 拍板：**
  1. 文體換成這 7 種＋8 個主題，新的 7 種為主。
  2. 通用的機制進 repo；品牌的內容（聲音、主題主張、標題與金句的寫法、退件累積的規則、色票字型）放 `EF_DATA` 當角色資料，不進 repo。
  3. 品牌角色放進現有的 `me`。之後還會有別的角色，所以角色資料夾是一份規格、每個角色都一樣，另做一頁角色管理（#116）。
  4. 舊的 12 種全部對到 7 種之一；舊工單保留舊 id，畫面顯示對到的新文體。
- **為什麼要寫成 ADR：** 文體清單決定 `harness/genres/`、分析報告的「建議文體」、訪談第 1 關、寫稿的輸入、程式檢查與錄音；角色資料夾的樣子決定之後每一個角色怎麼建。

## 2. 考量的選項

| 選項 | 結果 |
| :--- | :--- |
| 保留 12 種，另外加 7 種 | 不採用：兩套分類同時存在，訪談第 1 關與分析的「建議文體」不知道要用哪一套 |
| 7 種的定義連同品牌價值、CTA 整份放進 `harness/genres/` | 不採用：品牌內容會進 repo，別的角色也被迫帶著同一個品牌的價值 |
| 主題清單整份放角色資料，repo 不知道有哪些主題 | 不採用：主題是 front matter 的一欄，程式檢查與畫面要知道合法的值 |
| **7 種文體與 8 個主題的通用定義進 repo；各角色怎麼寫、帶什麼價值、對主題怎麼看放角色資料；舊 12 種用對照表顯示** | **採用** |

## 3. 決策

### 3.1 七種文體

每篇只有一個文體。slug 寫進文章的 front matter（`genre`）。

| slug | 文體 | 一句話 | 主證據 | 讀者讀完要做的決定 |
| :--- | :--- | :--- | :--- | :--- |
| `essay` | 隨筆 | 個人感受，或看了別人的分享有感而發 | 作者自己的經驗 | 不靠這一題分，看主證據 |
| `research-review` | 研究評論 | 一個領域或市場現在長什麼樣子，怎麼看它 | 一手報告與數據 | 要不要進這個市場、押這個方向 |
| `product-case` | 產品個案 | 拆一個產品為什麼這樣設計 | 作者親自使用的過程 | 自己的產品要怎麼設計 |
| `benchmark` | 實證評測 | 固定任務比較幾個方案，給出選型判斷 | 作者自己跑的測試 | 選哪一個方案 |
| `postmortem` | 工程復盤 | 一個專案從目標到失效到修正 | 作者自己的專案經驗 | 要避開哪個坑 |
| `explainer` | 理論教學 | 一個機制怎麼改變一個決定 | 論文或機制 | 怎麼判斷一個結果 |
| `trend` | 趨勢解讀 | 幾個新專案或公告背後的共同變化 | 一批新專案或公告 | 值不值得投入研究 |

- **判斷文體的方法：** 先問「這篇的主證據是什麼」，再問「讀者讀完要做哪個決定」。兩題的答案不一致時以主證據為準：沒有那種證據，就寫不了那種文體。
- **`product-case` 與 `benchmark` 一定要作者親自做過。** 沒有作者的實測或使用紀錄，不能選這兩種（ADR-0025 §3.2 第 3 關）。
- **通用定義放 `harness/genres/<slug>.md`**，一種一份：辨識訊號、必要內容、主證據、搜尋策略、推薦的結構公式（可以換）、骨架。這些不帶任何角色的價值或品牌。
- **沒有實際文章撐腰的文體只寫起始規範**；規則從寫出來的文章長出來，不預先發明。

### 3.2 主題

- 每篇只有一個主題。slug 寫進 front matter（`theme`）。跨兩個主題時，選讀者做決定時最在意的那一個。
- 8 個主題的 slug 與一句通用說明放在 `harness/genres/themes.md`：

| slug | 說明 |
| :--- | :--- |
| `worldview` | AI 時代的工作與職涯 |
| `builder-method` | 做產品的方法與工程實務 |
| `startup` | 新創的賽道與產品拆解 |
| `tech-selection` | 技術選型 |
| `adoption` | 落地導入與失敗復盤 |
| `education` | 決策原理與實作教學 |
| `tools` | 工具與工作流程選型 |
| `open-source` | 開源專案與技術演進 |

- **一個角色對每個主題怎麼看**（主張、常見的切入點）是那個角色的資料，放角色資料夾的 `themes.md`，不進 repo。角色可以只用其中幾個主題。
- 主題不是網站的分類：發布到哪個網站、歸到哪一類，是之後發布那一層的事，不在這份。

### 3.3 角色資料夾：每個角色同一種樣子

`$EF_DATA/authors/<角色>/`，不進 repo（ADR-0014）。格式範本放 `harness/templates/`，只寫格式與欄位說明，不放任何品牌內容。

| 檔 | 放什麼 | 沒有的時候 |
| :--- | :--- | :--- |
| `voice.md` | 這個角色怎麼說話：語氣、用字、節奏、舉例習慣、禁忌，包括句型這類可以用程式擋的規則（ADR-0025 §3.6） | 必要；沒有就不是一個角色 |
| `genres/<文體 slug>.md` | 這個角色寫這種文體的寫法、要多帶的價值、文末導去哪裡（CTA） | 標「未校準」，只用聲音＋通用定義寫（ADR-0015 §3.6） |
| `craft/` | 這個角色的寫作手藝：開場、標題、金句與收尾、圖文編排，一個主題一份 Markdown | 標題與金句先讀舊的共用規則 `$EF_DATA/style/headline-punchline-system.md`（相容舊設定）；其他項目沒有就不讀 |
| `themes.md` | 這個角色用哪幾個主題、對每個主題的主張 | 訪談第 1 關只列 `harness/genres/themes.md` 的通用說明 |
| `lessons.md` | 創作者退件或指正後累積的規則，一筆一條，新的在後；訪談與寫稿開工前讀最近十筆 | 不讀 |
| `brand.yaml` | 配圖用的色票、字型、封面預設（ADR-0027） | 用中性的預設值 |

- 寫稿只送這一篇用得到的檔：聲音、這個文體的風格檔、需要的 craft、最近十筆 lessons；不整包送，本機模型的上下文才塞得下，也省錢（ADR-0022 §3.5）。
- 創作者自己的品牌角色放進現有的 `me`。把現有的寫作系統拆進這個資料夾的匯入腳本進 repo，內容不進 repo（#106）。
- `lessons.md` 只有創作者在聊天裡同意的才寫進去（#114）；寫稿與訪談只讀。

### 3.4 舊的 12 種文類

舊 id 全部對到新 7 種之一。舊工單的 `job.md`、舊報告裡的「建議文類」保留原本的 id，畫面一律顯示對到的新文體；不改寫舊檔、不重跑。

| 舊 id | 舊名稱 | 顯示成 |
| :--- | :--- | :--- |
| `news` | 新聞快訊 | `trend` |
| `hot-take` | 熱點評論 | `essay` |
| `tutorial` | 教學文 | `explainer` |
| `tips` | 清單技巧 | `explainer` |
| `explainer` | 解說文 | `explainer` |
| `deep-dive` | 深度長文 | `research-review` |
| `notes` | 筆記摘要 | `explainer` |
| `review` | 評測比較 | `benchmark` |
| `case-study` | 案例拆解 | `product-case` |
| `opinion` | 觀點文 | `essay` |
| `story` | 故事心得 | `essay` |
| `roundup` | 精選彙整 | `trend` |

- 對照只影響顯示。新的分析、訪談、寫稿只用新的 7 種。
- `harness/conversions/` 的轉換說明是用舊 id 寫的，新的 7 種沒有對應；轉換說明本來就是選用的，這次不搬，真的需要時照新 slug 再寫。

## 4. 後果

- **正面：**
  - 文體直接告訴寫稿要拿哪一種證據、怎麼找資料、用什麼結構，不只是一副骨架。
  - 品牌的內容整份在角色資料夾裡，換一個角色就換一套聲音、價值、色票，repo 不用動。
  - 新角色照同一份規格建，角色管理頁（#116）只要認得這一種樣子。
- **負面：**
  - 分析報告的「建議文類」、`analyze` 與 `rewrite` 的錄音、文類相關的測試都要改、要重錄（#106）。
  - 舊的對照是有損的：例如舊的「教學文」「清單技巧」「筆記摘要」都顯示成理論教學，看不出原本的差別。
  - 只有起始規範的文體，寫出來可能不像樣，要靠實際寫過再補。
  - 共用的標題與金句規則與角色的 `craft/` 並存一段時間，直到每個角色都有自己的 craft。
- **影響範圍：** `harness/genres/`（12 個檔換成 7 個加 `themes.md`）、`harness/templates/`（角色資料夾的格式範本）、`harness/skills/investigate/`（建議文體）、`harness/skills/rewrite/`、`harness/recipes/rewrite.md`、`runner/stage_inputs.py`、`ui/present.py`（文體名稱與舊 id 的對照）、`list_personas`；錄音；PRD FR-RW-02；`CONTEXT.md` 的文體、主題、角色、文體風格、標題與金句規則。
- **重新評估觸發：** 常常有文章判不進 7 種之一；某個新角色需要 7 種以外的文體；或主題清單常常被各角色改成不同的一套。
