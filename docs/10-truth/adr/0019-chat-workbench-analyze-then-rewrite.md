# ADR-0019：聊天室工作台，先分析、再由人決定重構

> **狀態：** 已接受 | **日期：** 2026-10-13 | **決策者：** 專案擁有者
> 依 `docs/templates/vibecoding/04_architecture_decision_record_template.md` 撰寫。
> **取代：** ADR-0013（給目標就自動做完，人只審結果）。**修正：** ADR-0010（工單仍是資料夾裡的執行單位，但不再是使用者看到的東西；狀態從五種改成三種，見 §3.4）。
> 規劃原文：`30-snapshot/plans/2026-10-13-chat-workbench-replan.md`。
> **後續修正：ADR-0022**——流程不變；分析（brief、查證與找題材）與重構每一段都先用本機模型，失敗照 `fast`（Haiku 5.5）、`strong`（Sonnet 5.5）一級一級往上，對話的 Pi 預設 `fast`。

## 1. 背景與問題

- **上下文：** ADR-0013 把產品做成一條無人看管的產線：投入 → 整理 → 補料 → 二創 → 自動檢查 → 待審，人只在最後通過、退件或丟棄。UI 是看板加工單詳情。
- **2026-10-12 用 ihower 六篇文章實跑之後，創作者的修正：**
  - 工單不是重點，它只是每次對話的累積；介面最好是一個聊天室，像 ChatGPT 一樣能自己呼叫底層的 harness。
  - 想要的節奏是：丟文章、錄音或檔案 → 系統自動分析作者的內容 → 給一份研究題材的報告 → 他看完，再選設定好的角色與文體叫它重構。
  - 審稿就是作品交出來給人看，不需要通過、退件、丟棄這一套。
- **為什麼要寫成 ADR：** 這改了人在流程裡的位置（從只在最後，變成看完分析報告再決定）、主介面（從看板變成聊天室）與狀態模型（待審與審稿決定拿掉）；要改回來，UI、執行器的決定處理與 PRD 都要動。

## 2. 考量的選項

| 選項 | 結果 |
| :--- | :--- |
| 維持產線＋看板，只換掉整理與檢查的做法 | 不採用：創作者明確說工單與審稿不是重點，看板解的是他沒有的問題 |
| 回到 v1 的固定停點（選研究問題、定題 Gate） | 不採用：ADR-0013 否決它的理由仍然成立，固定表單把流程綁死 |
| **聊天室：分析與重構是兩件可以叫的工作，人在對話裡決定下一步** | **採用** |

## 3. 決策

1. **主介面是聊天室。** 每個對話是一個 Pi 的 RPC 程序（Pi 的長駐模式，JSONL 指令與事件），對話紀錄由 Pi 保存。瀏覽器送訊息、收事件串流。
2. **分析與重構分成兩件工作。** 在對話裡，Pi 用 ef-tools 的工具開工：`analyze` 照分析配方跑出分析報告，`rewrite` 照重構配方用指定的角色與文體寫文章。兩件工作之間停在對話裡，人可以追問、要求補查，或叫它寫；一句話叫它「分析完直接寫」也可以，不強制停。
3. **工作照舊由執行器照配方跑。** 一次分析或重構在資料夾裡仍是一張工單：段、嘗試、升級、預算預留、帳本、當機重跑不重付都不變（ADR-0010、ADR-0011）。對話的 Pi 只負責聽懂要做什麼、開工、把結果帶回對話；對話本身的模型呼叫也經閘道、記帳。
4. **拿掉待審與審稿決定。** 工單跑完就是完成、未完成或失敗，結果貼回對話。通過、退件、丟棄、決定檔與執行器套用決定都不做。要改文章就在對話裡說一句，系統帶著這句意見開一張新的重構工單（§3.6），產生新版本，舊版不覆寫。
   - 工單狀態只剩三種：`queued`、`running`、`done`（結束），另外保留當機時 `running` 回到 `queued` 的那一條。這一條改掉 ADR-0010 §3.1 的五種狀態。讀到舊的 `review`、`approved`、`discarded` 時一律當成 `done`，不報錯（2026-10-13 補，系統架構 session 審 ADR-0019、ADR-0020 時提出）。
5. **不變的底線**：不自動公開發布；不繞過付費牆；每段有最多嘗試次數、每次工作有預算；外來內容只當資料，不當指令。
6. **每一版都是一張新工單**（2026-10-13 補，系統架構 session 審 ADR-0019、ADR-0020 時提出）。補查、再改、換角色都開新工單，不在同一張單上再跑一次。
   - 理由：同一張單再跑一次，會撞上四件事：
     - 來源正文每張單只放一次（#72）。
     - 搜尋額度與故障看整本帳本。
     - 段輸入在第一次就凍結（#64）。
     - 去重會拿回舊單。
   - 新工單用對話的工單清單裡的 `version` 與 `parent` 串起來。需要上一版的產出時（例如補查要用原本的 brief，再改要用上一版文章），由執行器從上一張單複製進新工單的 `input/`。
   - 去重的鍵是「對話＋素材＋配方＋目標」；補查、再改、換角色一律不走去重。
   - ADR-0010 的「段／次」語意不變。

## 4. 後果

- **正面：**
  - 介面對上創作者實際的用法：先看懂、再決定寫不寫、用哪個角色寫。
  - 分析報告本身就是產出，可以累積成知識庫，不只是寫稿的中間檔。
  - 執行器、閘道、帳本、搜尋全部沿用，換掉的是最外層。
- **負面：**
  - 對話是長時間開著的 Pi 程序，閘道的工作鑰匙原本只在一段一次的 Pi 活著時有效，對話要另外定義鑰匙與它能碰的範圍，這是 T3 的改動。
  - 不再能無人看管地自動跑完整條；之後的訂閱源自動投入只能自動跑到分析報告，或在配方裡明寫「分析完直接寫」。
  - 已做好的看板、工單詳情與審稿區（S0.11）會被取代。
- **影響範圍：** PRD 的流程、使用者故事、FR-RV、FR-UI；`CONTEXT.md` 的待審、退件意見、決定檔；UI 資訊架構；路線圖。
- **重新評估觸發：** 創作者開始大量排程自動投入、不再逐篇看報告時，再評估要不要把「分析完直接寫」變成訂閱源的預設，並補回某種收件匣。
