## 1. 背景與問題

- **上下文：** ADR-0028 讓手機丟得進東西，但手機與桌面各自該長什麼樣沒有定；文章要改，現在只能打一句意見再開一張重構工單（ADR-0019 §3.6），改完要自己勾「跟上一版對照」才看得到差在哪，對照的版面也很陽春。
- **創作者 2026-10-16 看完兩份介面研究（語音寫作助理、手機與桌面分工）之後拍板：**
  1. AI 先用文字回答，之後再加聲音。原則是「用嘴巴講、用眼睛看」。
  2. 一位 AI、一個對話、一套記憶，手機和桌面畫面分工不同：手機是「捕捉」，桌面是「創作」。
  3. 口述改稿：創作者是「定方向」，不是逐條批改作業；AI 照語意整段修改，改完直接顯示修改前後對照（像 git 的紅綠對照），每次修改就是一個新版本，隨時可以回到前一版。
  4. 想法卡把 AI 對口述的處理分三種程度標出來，每一條都點得回錄音與逐字稿。
  5. 追問式訪談有三種模式；回到一個對話時，AI 先用一句話說上次講到哪。
  6. 記憶的同意照 lessons 的方式在畫面上按，這次不改。
- **要回答的事：** 手機首頁長什麼樣、哪些事不在手機上做；面板怎麼拆到第二個螢幕；口述改稿每次都開新工單，錢怎麼管、要不要每次問；對照以哪一版為基準；「整段依語意改」怎麼不改到沒被點到的段落；對照畫面長什麼樣。
- **為什麼要寫成 ADR：** 這改了改稿的開單方式與花錢的規矩（ADR-0019 §3.6、ADR-0021）、對照畫面的 token（ADR-0023），也替 P5a～P6b 的畫面定了分工。改回來要動閘道、對話工具、面板與路線圖。

## 2. 考量的選項

| 選項 | 結果 |
| :--- | :--- |
| 手機與桌面做成兩個 App、各有自己的助理 | 不採用：創作者要一位 AI、一個對話、一套記憶；兩套就會有「手機上講過、電腦上不知道」 |
| 口述改稿讓 AI 列出一條一條的修改建議，創作者逐條同意 | 不採用：創作者說那像在批改作業；他要定方向，看結果 |
| 有範圍時只讓模型交範圍內的新段落，程式把其他段原樣拼回去 | 不採用：照語意改常常要順手改一句銜接，硬拼回去段落會接不起來；改成讓它改、但範圍外的一律標出來（§3.5） |
| 每次口述改稿都跳出寫稿前那種花費確認卡 | 不採用：一次改稿五六輪就要按五六次，又回到批改作業的感覺 |
| 對照只用 ADR-0023 的靛藍淡底與淡灰刪除線 | 不採用：撰寫時暫定這樣做（紅色在這套介面只給擋下與失敗、Loomy 沒有綠、ADR-0023 為同一個畫面否決過紅綠），但創作者 2026-10-16 選了紅綠（PR #134）：一眼分得出加了什麼、刪了什麼，比顏色規則處處一致更重要；紅綠只在這個畫面用，其他地方照舊（§3.6） |
| **一個對話兩種畫面；口述改稿每次一張新工單、從改稿額度扣；對照以開始的那一版為基準、只在這個畫面用紅綠；範圍外的修改程式標出來** | **採用** |

## 3. 決策

### 3.1 AI 先用文字回答

- 創作者可以用說的（口述，ADR-0028 §3.7），AI 一律用文字回答，畫面上看。「用嘴巴講、用眼睛看」。
- AI 用聲音回答放 Later：要另選語音合成的供應商、經閘道記帳，到時再寫 ADR。

### 3.2 一位 AI、一個對話、一套記憶；手機捕捉、桌面創作

- **只有一位 AI、一個對話。** 手機與桌面打開的是同一個聊天室、同一個對話、同一個對話的 Pi（ADR-0019 §3.1、ADR-0028 隨身入口）。記憶（對話紀錄、編輯卡、角色的 lessons，之後的思想記憶）只有一套，哪一台丟進來的都看得到。兩邊只差在畫面怎麼排。
- **哪一種畫面看視窗寬度，不看裝置。** 窄的（手機直放）先看到捕捉畫面；寬的看到創作畫面。同一個網址，兩種畫面都能切過去。

**手機是捕捉畫面。** 打開 PWA 先看到：

- 一行大字「今天有什麼想法？」
- 三個大按鈕，由上往下，拇指按得到：
  1. **開始說話**：按下就錄，再按一下停；錄好的口述照 ADR-0028 §3.5 收進素材清單、轉文字。預設開一個新對話。
  2. **加入素材**：相簿、相機、檔案、貼連結，照 ADR-0028 的上限與素材清單。預設開一個新對話，也可以選放進哪一個。
  3. **繼續上次的討論**：打開最近動過的那個對話；P6 起先看到開場摘要（§3.9）。
- 對話清單收在次要的入口，不跟三個按鈕搶位置。
- **手機不做的事：** 長時間的編修（口述改稿、修改前後對照），以及比較來源（並排看幾篇來源或幾個版本）。這些入口在手機上只寫一句「這個在電腦上做」，不硬塞一個擠成一團的版本。手機上照樣可以聊天、讀報告與文章的最新版。在手機上明白要求改文章（「照這個改」「幫我把開頭改快一點」），跟在電腦上一樣算開始口述改稿，直接開改稿工單（同一位 AI、同一個對話，規矩見 §3.3）；結果卡在手機上看得到，對照要到電腦上看。

**桌面是創作畫面。** 就是現在的聊天室：左邊對話清單、中間對話、右邊成果面板（報告、文章、決策、花費）。

- **面板可以拆成獨立視窗**，拖到第二個螢幕：面板上一個「拆成視窗」的按鈕，用同一個網址的面板頁開一個新的瀏覽器視窗，原本的位置收起來，聊天欄變寬；關掉那個視窗，面板回到右邊。
- **兩個視窗是同一個對話，不是兩份資料。** 內容一律從伺服器讀；兩個視窗之間只傳「現在看哪一份、反白了哪幾段」這類畫面狀態（同源視窗之間的 `BroadcastChannel`）。在拆出去的面板上反白一段，聊天欄的輸入框就帶上那個範圍（§3.5）。
- 拆出去的視窗跟主視窗一樣走 ADR-0028 §3.2～§3.3 的進門檢查，不另開路。

### 3.3 口述改稿：創作者定方向，AI 照語意整段改

- **怎麼開始（手機與電腦同一條規矩）：** 有三種方式，任何一種都算開始：
  1. 在創作畫面，文章打開在面板上時，按「口述改稿」；
  2. 說「我們來改這篇」；
  3. 明白要求改文章，例如「照這個改」「幫我把開頭改快一點」。這一句本身就是第一個方向，直接開改稿工單，不用先按按鈕。
  - 開始之後，創作者說的話就是改稿的方向。
  - 只是評論或提問（「開頭有點慢」「這段的數字哪來的？」）不算開始，照舊只是評論（對話規則不變）；agent 可以回問一句「要我照這個改嗎？」，創作者說好才開單。
- **創作者講方向，不逐條批：** 用說的（也可以先在面板上反白一段，§3.5）講哪裡好、哪裡不好、想往哪裡走。對話的 agent 聽懂之後，用一句話說它要怎麼改、改哪幾段，接著直接開工，不列修改清單請創作者一條一條按同意。
- **AI 照語意整段改：** 改的單位是段落，不是逐字替換。一次口述講了好幾個方向，就是一次改稿、一張工單。
- **改完直接看對照：** 工單一結束，面板自動切到這一版的修改前後對照（§3.6），不用自己去勾。
- **改稿只改文章的寫法，不改編輯卡的決定。** 要換核心觀點、文體、主幹，照舊回訪談改那一關，再照編輯卡寫一篇（ADR-0025 §3.3）；對話的 agent 聽到這類方向時會這樣說。寫稿的規矩照舊：不替作者編經歷、不從記憶補事實、不多加編輯卡沒列的主張（`rewrite` skill、PRD §5）。
- **發不發出去由創作者決定。** EF 不發布（PRD §9），口述改稿也一樣。

### 3.4 每一次改稿是一張新工單（修正 ADR-0019 §3.6 的套法）

- **一次口述的方向＝一張改稿工單＝鏈上的一個新版本。** 照 ADR-0019 §3.6：開新工單，不在同一張單上再跑；上一版文章由執行器複製進新工單的 `input/`；不走去重。
- **`parent` 是這次改稿開始的那一版**，不一定是時間上最新的那一版：
  - 創作者看著 v3 說話，`parent` 就是 v3。
  - **agent 怎麼知道創作者在看哪一版：** 畫面送出每一則訊息時，一併帶面板上正在看的那一版的工單 id、反白的範圍（§3.5）與這則訊息的 id；對話主機把它們放在送給 Pi 的訊息最前面一行（`[ef-view …]`）。agent 改稿時拿那個工單 id 當 `from_job`，不自己猜「最新的一版」。
  - **隨時可以回到前一版：** 在面板的版本選單點回 v2，畫面就顯示 v2，不開單、不花錢；接著說話，就是從 v2 開一個分岔（版本號照 `CONTEXT.md`〈版本鏈〉的算法，同一個號碼可能出現兩次，畫面兩張都列）。
- **工單帶什麼：** `feedback` 是 agent 整理的一句方向，加上創作者原話的出處（那段口述在素材清單上的附件與時間範圍）；有範圍時帶 `scope`（§3.5）；`request_id` 與 `message_ids`（§3.7 防重複扣）。創作者原話不整段塞進去，跟 ADR-0025 §3.2 的「原話見 M<n>」同一個道理。
  - **`request_id` 怎麼來：** `message_ids` 是這次改稿涵蓋的那幾則訊息的 id（畫面在 `[ef-view]` 給的）。`request_id` 由閘道從它算：把 id 排序、用換行接起來、取 sha256 的前 16 個十六進位字。只有一則訊息就是那一則；幾則方向併成一次（下一點），就是那幾則，排序之後算出來的值跟 agent 送的順序無關。閘道在 `jobs.jsonl` 那一列記 `request_id` 與 `message_ids`。
- **帶範圍的改稿不能同時換角色或文體。** `rewrite` 同時給 `scope` 與 `persona` 或 `genre`，閘道拒絕：換角色或文體是整篇重寫，範圍沒有意義。
- **口述的方向不逐條確認。** ADR-0025 §3.2「口述先整理成條列請創作者確認」只管訪談的回答（那些會變成編輯卡上的決定）；改稿的確認就是看修改前後對照，不滿意就再說一次或回到前一版。
- **工單在跑的時候創作者又說了新的方向：** 每個對話同一時間最多一張工單在跑（ADR-0021 §3.4）照舊。新方向先收著（口述照樣進素材清單），這一張跑完、`[ef-job]` 通知到了，agent 把這段時間說的方向併成一次，從剛出來的那一版接著改。不另做排隊機制。
  - 併進來的方向如果帶著範圍，那個範圍是綁在當時看的那一版上的（§3.5），閘道照段落對齊換算到剛出來的那一版。**換算不過去就不開單，也不自動改成整篇改：** 那個方向留著等，agent 跟創作者說是哪一段在新的一版對不上（「你剛才說的第 5 段，在新的一版被拆掉了」），等創作者二選一：重新指一次（反白或說哪一段，是新的範圍），或明白說「整篇改」。沒有範圍的重送只在創作者明白這樣說之後才做，agent 不自己重送。

### 3.5 改稿範圍與範圍外的修改

- **段落有編號。** 創作畫面上，文章面板的每一段在左邊留白處標段號（標題、段落、清單的一項各算一段，跟對照用的切法同一套）。創作者可以說「第 5 段」。
- **兩種給範圍的方法：**
  1. **反白：** 在面板上反白一段文字，輸入框上方出現一個小標籤「範圍：第 5～6 段」，可以按掉。反白跨到哪幾段就是哪幾段。
  2. **用說的：** 「第 5 段」「開頭那段」「講價格那段」。agent 讀文章（`read_article`）對出段號，開工前那一句話裡講出它對到哪幾段（「我改第 5、6 段」）。對錯了，看對照就知道，回到前一版再說一次。
- **範圍綁在創作者看的那一版上，不只記段號。** `rewrite` 的 `scope` 是 `{job, paragraphs}`：`job` 是創作者反白或說話時面板上那一版的工單 id，`paragraphs` 是那一版的段號，每段附它的段落雜湊（下面定義）。反白的範圍由畫面算好雜湊、經 `[ef-view]` 交給 agent 照抄；agent 用說的對出來的段號沒有雜湊，由閘道從 `job` 那一版的文章補上。畫面送來的雜湊，閘道開單前用 `job` 那一版的文章重算，對不上就拒絕（範圍跟檔案不符）。修正 ADR-0021 §3.4。
- **段落雜湊怎麼算（畫面與閘道一字不差地照做）：**
  1. 從文章的 Markdown 原文開始，不是畫面渲染出來的字；先拿掉 front matter（`ui/artifacts.py` 的 `without_front_matter`）。
  2. 切段用 `ui/artifacts.py` 的 `_units`，就是段號與對照用的同一套：空行分段，標題與清單的每一項各自一段。每段得到它的種類（`h1`～`h6`、`p`、`li-ul`、`li-ol`）與它的 Markdown 原文（去掉行首的 `#`、`-`、`1.` 這類記號，行內的 Markdown 照留）。
  3. 正規化：先做 Unicode NFC，再把每一串 Unicode 空白（含全形空白與換行）換成一個半形空格，最後去掉頭尾空白。
  4. 雜湊：`種類 + 換行 + 正規化後的原文`，用 UTF-8 編碼算 sha256，取前 16 個十六進位字（小寫）。種類放進去，是為了同樣的字當標題與當段落時分得開。
  - 實作票要有一組畫面（JavaScript）與閘道（Python）共用的測試向量：同一批段落（含中英混排、全形空白、NFC 與 NFD 兩種寫法的同一個字、標題與段落同字），兩邊算出來要一樣。
- **範圍跟 `from_job` 不是同一版時（併進來的方向，§3.4）：** 閘道用跟對照同一套的段落對齊，把 `job` 那一版的每一段換算到 `from_job` 那一版：對齊成「沒改」或「一對一改過」的段落算對得上，換成那一版的段號。有任何一段對不上（被刪、被拆、被併），就拒絕開單，回「範圍換算不過去」與是哪幾段；之後照 §3.4 等創作者重新指或明白說整篇改，不自動拿掉範圍重送。幾個方向併成一次時，範圍取聯集；其中一個方向本來就沒有範圍（創作者說的就是整篇），就是整篇都能改。
- 寫稿工單的任務說明列出範圍內的段落，skill 規定範圍外的段落一字不改。沒給範圍就是整篇都可以改。
- **範圍外的修改由程式標出來，不擋：** 工單結束後，程式用跟對照同一套的段落對齊比 `parent` 與新版（只在有範圍時做）：
  - **範圍外的每一段都要比**，不只看對齊後相鄰的：`parent` 裡範圍外的每一段，在新版都要對齊成「沒改」；改了、被刪了，都算範圍外的修改。
  - **範圍的位置：** 範圍內連續的 k 段，在新版的位置是「它前面最近一段沒改的範圍外段落」與「它後面最近一段沒改的範圍外段落」之間的那幾段。這裡面可以是 k−1 到 k+1 段（拆一段成兩段、或把兩段併成一段，各最多一次）；多出來的段落算範圍外。範圍不連續就一塊一塊各自算。
  - **其他地方多出來的段落**，一律算範圍外，沒有「緊貼著範圍就算在內」的例外。
  - **參考來源一節（`## 參考來源` 與它底下的清單）永遠不算範圍外**：改稿可能多用或少用一個來源，參考資料本來就要跟著變。
  - **front matter：** `diff_articles` 現在比對前會把 front matter 拿掉（`ui/artifacts.py`），所以 front matter 的 `title`、`description`、`genre`、`theme` 有改時，在對照頂端另外列一行「front matter 改了：…」，有沒有範圍都列。有範圍時，front matter `title` 只有在範圍包含文章的一級標題那一段時才不算範圍外；`description`、`genre`、`theme` 有範圍時改了都算範圍外。
  - 範圍外的修改在對照上標「範圍外」（§3.6），對照頂端寫「範圍外改了 N 處」。
  - **不算這一次失敗、不重跑。** 重跑要再花錢，而且那可能是一句必要的銜接；要不要留由創作者看了決定：留著就好；不要就回到前一版，或說「範圍外的改回去」再改一次。
  - 每張單有幾處範圍外的修改，記在工單的結果裡，量得到（§4 重新評估觸發）。
- 這個檢查只用程式，不經過模型（PRD §7）。

### 3.6 修改前後對照長什麼樣

這一段只描述，不是設計稿；畫面要比現在面板上的「跟 vN 對照」好看，實作票先出設計稿給創作者看。

- **基準：** 預設對這一版開始的那一版（`parent`），因為創作者就是看著那一版說話的；標頭寫「v4 對照 v3」與那次的方向（「你 14:05 說的：開頭太長，例子換成自己的」）。版本選單可以換成鏈上的任何一版來比（例如對第 1 版看總共改了多少），不花錢。
- **一欄讀下去（預設）：** 照新版的順序讀，像讀一篇文章：
  - 加上的字：綠色淡底（`--diff-insert`），字仍是墨色；
  - 刪掉的字：紅色淡底（`--diff-delete`）、次要字色加刪除線，放在加上的字前面；
  - 有改的段落，左邊留白處一條細線加一個記號：只加了字是綠的 `+`、只刪了字是紅的 `−`（`--diff-insert-mark`、`--diff-delete-mark`），兩種都有是次要字色的 `±`；整段刪掉的收成一行淡灰「刪掉一段：開頭幾個字…」，點開才看全文；
  - 改句子時以句子為單位標，不把一句話切成一堆碎字。
- **頂端一列：** 改了幾段、加了幾段、刪了幾段；「上一處／下一處」跳到下一個有改的地方；「只看有改的段落」把沒改的連續段落收成一行「⋯ 4 段沒改 ⋯」。
- **範圍外的修改：** 那一段旁邊一個「範圍外」的小標籤，圖示＋文字＋顏色三件一組（ADR-0007 §3.3）。顏色用「要你判斷」的黃當底、字用 `--color-on-action`（`--diff-outside`，見下面的表）；黃不跟紅綠搶，因為它的意思是「這裡要你看」，不是加或刪。
- **寬螢幕（拆出去的面板放在第二個螢幕）：** 可以切成左右兩欄，左邊改之前、右邊改之後，段落對齊；預設仍是一欄。
- **讀起來舒服：** 文章用 `--font-reading-serif`，一行大約 30～35 個中文字；標記不改行高；不放動畫（NFR-OBS-02 的精神）。
- **不只靠顏色分：** 紅綠是色覺不方便的人最難分的一對，所以加上的字用 `<ins>`、刪掉的用 `<del>`，刪掉的一定有刪除線，左邊的 `+`、`−` 記號一定在；只看形狀也分得出加了什麼、刪了什麼（ADR-0007 §3.3 第一條）。
- **顏色：像 git 的紅綠，只在這個畫面**（創作者 2026-10-16 在 PR #134 拍板，取代撰寫時暫定的靛藍與淡灰）。
  - 刪掉的是紅、加上的是綠，一眼看出改了什麼。這是例外，**只在修改前後對照裡**：其他所有畫面，紅色照舊只代表擋下、失敗（ADR-0007 §3.2），綠色不用在別的地方。
  - 紅用 Loomy 現有的 `--color-danger`。Loomy 沒有綠，所以加一個 EF 自己的基礎值 `--ef-color-green`：淺色 `#1a7f37`，深色與跟隨系統 `#3fb950`。名字用 `--ef-` 開頭，一看就知道不是 Loomy 的；值放在 `tokens.css` 檔尾另外標出的一段，不混進從 Loomy 搬來的值（修正 ADR-0007 §3.1：第 1 點「基礎 token 用 Loomy 的」與第 2 點「狀態 token 的值一律是 Loomy 顏色的別名」，各多這一個例外）。
  - 大面積只用淡底（跟 ADR-0023 一樣用 `--provenance-fill` 的比例），字照舊是墨色或次要字色，讀起來不刺眼；飽和的紅綠只用在記號與左邊的細線。

  | token | 意思 | 值 |
  | :--- | :--- | :--- |
  | `--diff-insert` | 加上的字的底色 | `color-mix(in srgb, var(--ef-color-green) var(--provenance-fill), transparent)`，字是墨色 |
  | `--diff-delete` | 刪掉的字的底色 | `color-mix(in srgb, var(--color-danger) var(--provenance-fill), transparent)`，字是 `--color-text-secondary` 加刪除線 |
  | `--diff-insert-mark` | `+` 記號與左邊細線 | `--ef-color-green` |
  | `--diff-delete-mark` | `−` 記號與左邊細線 | `--color-danger` |
  | `--diff-outside` | 「範圍外」標籤的底色 | `--color-accent-action`（實黃），字用 `--color-on-action` |

  - `--diff-insert`、`--diff-delete` 名字不變、值換掉；`--diff-delete` 從「字色」變成「底色」，`chat.css` 的 `del.ch-del` 要跟著改（實作票做）。
  - **對比照 WCAG AA（一般文字至少 4.5:1）**，用 `tokens.css` 的值算（底色以 `--provenance-fill` 的 12% 疊在頁面底色上）：

  | 組合 | 淺色 | 深色 |
  | :--- | :--- | :--- |
  | `+` 記號（綠）對頁面底色 | 5.08:1 | 6.70:1 |
  | `−` 記號（紅）對頁面底色 | 5.44:1 | 6.10:1 |
  | 墨色字對綠淡底 | 14.31:1 | 12.62:1 |
  | 次要字色對紅淡底（刪掉的字） | 5.92:1 | 8.53:1 |

  - Loomy 改了 `--color-danger` 或頁面底色、或之後換了綠的值，要重算這張表；低於 4.5:1 就不能用。

### 3.7 改稿的錢：對話的改稿額度

- **問題：** 每一次改稿都是一張要花錢的工單（本機先試，失敗才升到雲端，ADR-0022；一張的上限是費用設定的改稿預算，預設 US$0.50）。寫一篇新文章前有一張最後確認卡（寫預估金額與上限）；改稿現在不問。口述改稿一次會改好幾輪，每輪都跳確認卡太煩，完全不問又可能在沒注意時一直開單。
- **決定：每個對話有一份改稿額度**（創作者 2026-10-16 在 PR #134 確認）。
  - 對話裡第一次要改稿時，畫面出一張確認卡：「接下來最多再改 N 次，每次最多 US$X，最多共 US$N×X」，按「好」才開第一張。之後每次改稿從額度扣一次，不再問。N 預設 5，X 是當下費用設定的改稿預算，都在費用設定頁可以改。
  - **給額度的紀錄：** `$EF_DATA/conversations/<對話 id>/revision-allowance.jsonl`，只增不改，一次給一行：給額度的 id、核准的次數 N、當時的每次上限 X、時間、`source: ui`。
  - **誰寫：** 對話主機。畫面按「好」或「再給 N 次」→ 對話主機的 API 直接寫這份紀錄（跟 #107 的編輯卡入口、PR #130 的 lessons 核准同一種做法）。`allow_revisions` 列在 `UI_ONLY_TOOLS`，閘道的 `/tools/` 拿任何鑰匙來叫一律拒絕，對話的 Pi 叫不到。閘道只讀這份紀錄。
  - **開單時扣，失敗不退。** `rewrite` 在 `open_and_record_locked` 同一把鎖裡（對話的開單鎖），先決定這張單用哪一筆額度、再開單、再把這張單記進 `jobs.jsonl`（那一列標它是改稿，帶 `grant_id`、`request_id`、`message_ids`）。記這一列就是扣，跟開單同一步，不會只扣不開或只開不扣。工單後來失敗或未完成，額度不退：錢可能已經花了。對話主機寫給額度的紀錄時也拿同一把鎖。
  - **用哪一筆額度：先給的先用（FIFO）。** 照 `revision-allowance.jsonl` 的順序，找第一筆還有剩的：那一筆剩幾次 = 它的 N 減掉 `jobs.jsonl` 裡帶著它的 `grant_id` 的改稿單數。每一筆各自算，不把幾筆的次數加在一起。都沒剩就是用完。
  - **防重複扣：** 這次的 `message_ids` 裡任何一個 id 已經記在某張改稿單上，就拿回那一張、不再扣（agent 重送、連按兩下、併過的方向其中一則被重送，都對到同一張）；`request_id` 一樣的也一樣。兩個請求同時來，鎖讓它們一個一個查，不會都以為還有額度。
  - **每次上限照付錢的那一筆：** 改稿工單的預算 = 「現在費用設定的改稿預算」與「付這張單的那一筆額度記下的 X」取小的。之後把設定調高，每一筆也不會超過創作者按「好」時看到的 N×X。
  - **用完時：** 閘道拒絕開單（說是額度用完，不是別的錯），同時通知對話主機推一則 `ef_allowance` 給畫面，出那張確認卡；agent 跟創作者說一聲，方向先收著。創作者按「再給 N 次」之後，對話主機送一則 `[ef-allowance]` 通知給 agent，請它把等著的那個方向重送（同一個 `request_id`）。
  - **只管 `rewrite`：** 照編輯卡寫一篇新文章（`write_from_card`）不用額度，照舊用它自己的最後確認卡。
  - **一條規矩管所有改稿：** 打字的「照這個改」與口述的方向都是對話的 agent 叫 `rewrite`，閘道分不出也不該分，所以額度管的是每一次 `rewrite`。這會讓現在打字改稿的第一次多一張確認卡，是行為改變，創作者確認過。
  - 對照頂端寫這一輪改了幾次、花了多少、額度還剩幾次。
  - 每月上限、對話同時一張單照舊（ADR-0021 §3.3、§3.4，ADR-0027 §3.6）。
- **為什麼這樣定：** 第一次就讓創作者看到最壞要花多少，之後不打斷；ADR-0021 §4 列過「一個對話開超過 N 張單要創作者確認」這個方向，這是它在改稿上的版本。創作者要每次都問、或完全不問，改 N 就好（N 設很大就等於不問）。

### 3.8 想法卡：三種處理程度，每一條點得回錄音（P5b）

- **AI 對口述的處理分三種程度，每一條都標出來：**
  1. **只清贅字**：嗯、啊、重複的字拿掉，意思與用詞不動。
  2. **重新排順序**：把散在各處講的同一件事排在一起；標出搬動了哪幾條（原本在第幾句）。
  3. **補了證據或例子**：AI 從這個對話的素材清單、報告與來源補的；標「不是你說的」，並指出補自哪裡。不准從模型的記憶補事實，也不准替創作者補親身經驗（PRD §5、ADR-0025 §3.2 第 3 關的規矩）。
- **每一條都點得回錄音和逐字稿的那一段**（逐字稿帶時間戳，ADR-0028 §3.7）。「補了」的那一條指回它要撐的那句話所在的那一段，另外指出它自己的出處。指不回去的標出來，不假裝有出處（FR-ID-03）。
- 補的那一條不是創作者說的，所以不標 `speaker: creator`，標 `speaker: ai`；仍然是暫定（`status: tentative`）。

### 3.9 追問式訪談的三種模式與回來時的開場摘要（P6）

- **三種模式，隨時可以換**（說一聲或按畫面上的模式標籤）：
  1. **只聽不插話**：AI 不問問題，只簡短表示收到；創作者說「好了」再整理（例如整理成想法卡）。適合邊走邊講。
  2. **追問**：一次一題追問缺口，可以略過、可以「稍後研究」（路線圖 P6 原本的做法）。預設這一種。
  3. **扮反方**：AI 扮演最強的反對意見，壓力測試創作者的論點。畫面上標「AI 扮的反方」，不是 AI 的立場，也不記成創作者的立場；反方用到的事實只能來自報告、來源與素材，沒有就用問句（「如果有人拿出相反的數據呢？」），不編事實。
- 模式記在對話裡；換模式時對話主機通知 agent，跟 `[ef-card]` 一樣。答案要進編輯卡，照舊經訪談的工具與規矩記（ADR-0025）。
- **回到一個對話時的開場摘要：** 創作者離開一段時間（預設 2 小時，可以改；創作者 2026-10-16 確認）後再打開一個對話，AI 先用一句話說上次講到哪、還有什麼沒做。
  - 只依記下來的東西說：編輯卡的狀態、跑完與沒跑完的工單、素材清單上還沒處理的附件、等著按的 lesson 提議。不憑印象猜。
  - 一次回來只寫一次，寫成對話裡一則一般的訊息；短時間內重開不再寫。花的是對話的模型錢（`fast`），記在對話的帳本。

### 3.10 記憶的同意照舊在畫面上按

- 會改變創作者之後寫作的記憶，照 lessons 的方式：agent 只能提議，創作者在畫面上按同意，閘道才寫（ADR-0026 §3.3，lessons 的實作見 PR #130）。之後的思想記憶照同一條規矩。這次不改。

## 4. 後果

- **正面：**
  - 手機打開就知道要幹嘛：講、丟、接著聊；桌面專心做長時間的編修，第二個螢幕放對照。
  - 改稿從「打一句、開單、自己勾對照」變成「講一句、直接看修改前後對照」，改了什麼一眼看出；範圍外的修改躲不掉。
  - 每一輪改稿都是一個版本，隨時退得回去；錢在第一次就講清楚最多多少。
  - 想法卡分得出哪句是創作者說的、哪句是 AI 補的。
- **負面：**
  - 手機與桌面的畫面要各做一套版面；拆出去的視窗要跟主視窗同步畫面狀態。
  - 改稿額度讓現在打字改稿的第一次多一張確認卡。
  - 範圍外的修改只標不擋：模型常常不守範圍時，創作者要多看、多退版。
  - 開場摘要每次回來花一次對話的模型錢；扮反方的回答要靠畫面標示，不讓人誤以為是查證過的事實。
  - 紅色在這個畫面是「刪掉的字」，在其他地方是「擋下、失敗」：同一個顏色兩個意思，只靠「只在修改前後對照裡」這條界線分；綠色是 Loomy 以外多出來的一個值，同步 Loomy 時要記得留著。
