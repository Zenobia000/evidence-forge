# ADR-0029：手機捕捉、桌面創作；口述改稿與修改前後對照

> **狀態：** 已接受（創作者 2026-10-16 拍板；PR 合併即生效。標「待創作者確認」的幾處是撰寫時的提案） | **日期：** 2026-10-16 | **決策者：** 專案擁有者
> 依 `docs/templates/vibecoding/04_architecture_decision_record_template.md` 撰寫。
> **修正：** ADR-0019 §3.6——「每一版都是一張新工單」在口述改稿時怎麼套：一次口述的方向開一張改稿工單，`parent` 是它開始的那一版，帶改稿範圍；改稿從對話的改稿額度扣（§3.4、§3.7）。ADR-0021 §3.4——`rewrite` 多一個 `scope`（改稿範圍）參數；畫面多一個對話的 Pi 叫不到的入口 `allow_revisions`，由閘道記（§3.5、§3.7）。ADR-0023 §2、§3.1——文章對照改叫「修改前後對照」，照舊用 `--diff-insert`、`--diff-delete`，多一個標範圍外修改的別名，版面重做（§3.6）。ADR-0025 §3.2——「口述先整理成條列請創作者確認」只管訪談的回答；口述改稿的方向不逐條確認，修改前後對照就是確認（§3.4）。ADR-0028 §3.4——PWA 在手機上打開先看到捕捉畫面（§3.2）；§5 寫的「思想記憶（ADR-0029）」「配方平行展開（ADR-0030）」只是當時預定的號碼，0029 給了這一份，那兩份開工時用下一個空號（§5）。
> 票：#132。

## 1. 背景與問題

- **上下文：** ADR-0028 讓手機丟得進東西，但手機與桌面各自該長什麼樣沒有定；文章要改，現在只能打一句意見再開一張重構工單（ADR-0019 §3.6），改完要自己勾「跟上一版對照」才看得到差在哪，對照的版面也很陽春。
- **創作者 2026-10-16 看完兩份介面研究（語音寫作助理、手機與桌面分工）之後拍板：**
  1. AI 先用文字回答，之後再加聲音。原則是「用嘴巴講、用眼睛看」。
  2. 一位 AI、一個對話、一套記憶，手機和桌面畫面分工不同：手機是「捕捉」，桌面是「創作」。
  3. 口述改稿：創作者是「定方向」，不是逐條批改作業；AI 照語意整段修改，改完直接顯示修改前後對照（像 git 的紅綠對照），每次修改就是一個新版本，隨時可以回到前一版。
  4. 想法卡把 AI 對口述的處理分三種程度標出來，每一條都點得回錄音與逐字稿。
  5. 追問式訪談有三種模式；回到一個對話時，AI 先用一句話說上次講到哪。
  6. 記憶的同意照 lessons 的方式在畫面上按，這次不改。
- **要回答的事：** 手機首頁長什麼樣、哪些事不在手機上做；面板怎麼拆到第二個螢幕；口述改稿每次都開新工單，錢怎麼管、要不要每次問；對照以哪一版為基準；「整段依語意改」怎麼不改到沒被點到的段落；對照畫面長什麼樣。
- **為什麼要寫成 ADR：** 這改了改稿的開單方式與花錢的規矩（ADR-0019 §3.6、ADR-0021）、對照畫面的 token（ADR-0023），也替 P5a～P6b 的畫面定了分工。改回來要動閘道、對話工具、面板與路線圖。

## 2. 考量的選項

| 選項 | 結果 |
| :--- | :--- |
| 手機與桌面做成兩個 App、各有自己的助理 | 不採用：創作者要一位 AI、一個對話、一套記憶；兩套就會有「手機上講過、電腦上不知道」 |
| 口述改稿讓 AI 列出一條一條的修改建議，創作者逐條同意 | 不採用：創作者說那像在批改作業；他要定方向，看結果 |
| 有範圍時只讓模型交範圍內的新段落，程式把其他段原樣拼回去 | 不採用：照語意改常常要順手改一句銜接，硬拼回去段落會接不起來；改成讓它改、但範圍外的一律標出來（§3.5） |
| 每次口述改稿都跳出寫稿前那種花費確認卡 | 不採用：一次改稿五六輪就要按五六次，又回到批改作業的感覺 |
| 對照照字面用紅與綠 | 不採用（待創作者確認）：這套介面的紅色只給擋下與失敗，Loomy 沒有綠色，ADR-0023 也已經為同一個畫面否決過；改用 ADR-0023 的兩個 token 做到「一眼分得出加了什麼、刪了什麼」（§3.6） |
| **一個對話兩種畫面；口述改稿每次一張新工單、從改稿額度扣；對照以開始的那一版為基準；範圍外的修改程式標出來** | **採用** |

## 3. 決策

### 3.1 AI 先用文字回答

- 創作者可以用說的（口述，ADR-0028 §3.7），AI 一律用文字回答，畫面上看。「用嘴巴講、用眼睛看」。
- AI 用聲音回答放 Later：要另選語音合成的供應商、經閘道記帳，到時再寫 ADR。

### 3.2 一位 AI、一個對話、一套記憶；手機捕捉、桌面創作

- **只有一位 AI、一個對話。** 手機與桌面打開的是同一個聊天室、同一個對話、同一個對話的 Pi（ADR-0019 §3.1、ADR-0028 隨身入口）。記憶（對話紀錄、編輯卡、角色的 lessons，之後的思想記憶）只有一套，哪一台丟進來的都看得到。兩邊只差在畫面怎麼排。
- **哪一種畫面看視窗寬度，不看裝置。** 窄的（手機直放）先看到捕捉畫面；寬的看到創作畫面。同一個網址，兩種畫面都能切過去。

**手機是捕捉畫面。** 打開 PWA 先看到：

- 一行大字「今天有什麼想法？」
- 三個大按鈕，由上往下，拇指按得到：
  1. **開始說話**：按下就錄，再按一下停；錄好的口述照 ADR-0028 §3.5 收進素材清單、轉文字。預設開一個新對話。
  2. **加入素材**：相簿、相機、檔案、貼連結，照 ADR-0028 的上限與素材清單。預設開一個新對話，也可以選放進哪一個。
  3. **繼續上次的討論**：打開最近動過的那個對話；P6 起先看到開場摘要（§3.9）。
- 對話清單收在次要的入口，不跟三個按鈕搶位置。
- **手機不做的事：** 長時間的編修（口述改稿、修改前後對照），以及比較來源（並排看幾篇來源或幾個版本）。這些入口在手機上只寫一句「這個在電腦上做」，不硬塞一個擠成一團的版本。手機上照樣可以聊天、讀報告與文章的最新版；在手機上說「照這個改」照樣會開改稿工單（同一位 AI、同一個對話），結果卡在手機上看得到，對照要到電腦上看。

**桌面是創作畫面。** 就是現在的聊天室：左邊對話清單、中間對話、右邊成果面板（報告、文章、決策、花費）。

- **面板可以拆成獨立視窗**，拖到第二個螢幕：面板上一個「拆成視窗」的按鈕，用同一個網址的面板頁開一個新的瀏覽器視窗，原本的位置收起來，聊天欄變寬；關掉那個視窗，面板回到右邊。
- **兩個視窗是同一個對話，不是兩份資料。** 內容一律從伺服器讀；兩個視窗之間只傳「現在看哪一份、反白了哪幾段」這類畫面狀態（同源視窗之間的 `BroadcastChannel`）。在拆出去的面板上反白一段，聊天欄的輸入框就帶上那個範圍（§3.5）。
- 拆出去的視窗跟主視窗一樣走 ADR-0028 §3.2～§3.3 的進門檢查，不另開路。

### 3.3 口述改稿：創作者定方向，AI 照語意整段改

- **怎麼開始：** 在創作畫面，文章打開在面板上時，按「口述改稿」（或直接說「我們來改這篇」）。之後創作者說的話就是改稿的方向；沒開口述改稿時，對一篇文章的評論或提問照舊只是評論（對話規則不變）。
- **創作者講方向，不逐條批：** 用說的（也可以先在面板上反白一段，§3.5）講哪裡好、哪裡不好、想往哪裡走。對話的 agent 聽懂之後，用一句話說它要怎麼改、改哪幾段，接著直接開工，不列修改清單請創作者一條一條按同意。
- **AI 照語意整段改：** 改的單位是段落，不是逐字替換。一次口述講了好幾個方向，就是一次改稿、一張工單。
- **改完直接看對照：** 工單一結束，面板自動切到這一版的修改前後對照（§3.6），不用自己去勾。
- **改稿只改文章的寫法，不改編輯卡的決定。** 要換核心觀點、文體、主幹，照舊回訪談改那一關，再照編輯卡寫一篇（ADR-0025 §3.3）；對話的 agent 聽到這類方向時會這樣說。寫稿的規矩照舊：不替作者編經歷、不從記憶補事實、不多加編輯卡沒列的主張（`rewrite` skill、PRD §5）。
- **發不發出去由創作者決定。** EF 不發布（PRD §9），口述改稿也一樣。

### 3.4 每一次改稿是一張新工單（修正 ADR-0019 §3.6 的套法）

- **一次口述的方向＝一張改稿工單＝鏈上的一個新版本。** 照 ADR-0019 §3.6：開新工單，不在同一張單上再跑；上一版文章由執行器複製進新工單的 `input/`；不走去重。
- **`parent` 是這次改稿開始的那一版**，不一定是時間上最新的那一版：
  - 創作者看著 v3 說話，`parent` 就是 v3。
  - **隨時可以回到前一版：** 在面板的版本選單點回 v2，畫面就顯示 v2，不開單、不花錢；接著說話，就是從 v2 開一個分岔（版本號照 `CONTEXT.md`〈版本鏈〉的算法，同一個號碼可能出現兩次，畫面兩張都列）。
- **工單帶什麼：** `feedback` 是 agent 整理的一句方向，加上創作者原話的出處（那段口述在素材清單上的附件與時間範圍）；有範圍時帶 `scope`（§3.5）。創作者原話不整段塞進去，跟 ADR-0025 §3.2 的「原話見 M<n>」同一個道理。
- **口述的方向不逐條確認。** ADR-0025 §3.2「口述先整理成條列請創作者確認」只管訪談的回答（那些會變成編輯卡上的決定）；改稿的確認就是看修改前後對照，不滿意就再說一次或回到前一版。
- **工單在跑的時候創作者又說了新的方向：** 每個對話同一時間最多一張工單在跑（ADR-0021 §3.4）照舊。新方向先收著（口述照樣進素材清單），這一張跑完、`[ef-job]` 通知到了，agent 把這段時間說的方向併成一次，從剛出來的那一版接著改。不另做排隊機制。

### 3.5 改稿範圍與範圍外的修改

- **段落有編號。** 創作畫面上，文章面板的每一段在左邊留白處標段號（標題、段落、清單的一項各算一段，跟對照用的切法同一套）。創作者可以說「第 5 段」。
- **兩種給範圍的方法：**
  1. **反白：** 在面板上反白一段文字，輸入框上方出現一個小標籤「範圍：第 5～6 段」，可以按掉。反白跨到哪幾段就是哪幾段。
  2. **用說的：** 「第 5 段」「開頭那段」「講價格那段」。agent 讀文章（`read_article`）對出段號，開工前那一句話裡講出它對到哪幾段（「我改第 5、6 段」）。對錯了，看對照就知道，回到前一版再說一次。
- **範圍怎麼傳：** `rewrite` 多一個 `scope` 參數，是 `parent` 那一版的段號清單（修正 ADR-0021 §3.4）。寫稿工單的任務說明列出這幾段，skill 規定範圍外的段落一字不改。沒給範圍就是整篇都可以改。
- **範圍外的修改由程式標出來，不擋：**
  - 工單結束後，程式用跟對照同一套的段落對齊，比 `parent` 與新版：範圍外的段落有改、被刪，或在離範圍不相鄰的地方多出新段落，就是範圍外的修改。緊貼著範圍前後多出的新段落（把一段拆成兩段）算在範圍內。標題與 front matter 的 `title`、`description` 改了，範圍沒包含標題時也算範圍外。
  - 範圍外的修改在對照上標「範圍外」（§3.6），對照頂端寫「範圍外改了 N 處」。
  - **不算這一次失敗、不重跑。** 重跑要再花錢，而且那可能是一句必要的銜接；要不要留由創作者看了決定：留著就好；不要就回到前一版，或說「範圍外的改回去」再改一次。
  - 每張單有幾處範圍外的修改，記在工單的結果裡，量得到（§4 重新評估觸發）。
- 這個檢查只用程式，不經過模型（PRD §7）。

### 3.6 修改前後對照長什麼樣

這一段只描述，不是設計稿；畫面要比現在面板上的「跟 vN 對照」好看，實作票先出設計稿給創作者看。

- **基準：** 預設對這一版開始的那一版（`parent`），因為創作者就是看著那一版說話的；標頭寫「v4 對照 v3」與那次的方向（「你 14:05 說的：開頭太長，例子換成自己的」）。版本選單可以換成鏈上的任何一版來比（例如對第 1 版看總共改了多少），不花錢。
- **一欄讀下去（預設）：** 照新版的順序讀，像讀一篇文章：
  - 加上的字：`--diff-insert`（靛藍淡底，「AI 動過」，ADR-0007 §3.2）；
  - 刪掉的字：`--diff-delete`（淡灰加刪除線），放在加上的字前面；
  - 有改的段落，左邊留白處一條靛藍細線，加一個 `+`、`−` 或 `±` 的記號；整段刪掉的收成一行淡灰「刪掉一段：開頭幾個字…」，點開才看全文；
  - 改句子時以句子為單位標，不把一句話切成一堆碎字。
- **頂端一列：** 改了幾段、加了幾段、刪了幾段；「上一處／下一處」跳到下一個有改的地方；「只看有改的段落」把沒改的連續段落收成一行「⋯ 4 段沒改 ⋯」。
- **範圍外的修改：** 那一段旁邊一個「範圍外」的小標籤，圖示＋文字＋顏色三件一組（ADR-0007 §3.3）。顏色用「要你判斷」的黃當底、字用 `--color-on-action`；新的別名 `--diff-outside` 指向 `--color-accent-action`，跟 `--verify-disputed` 用同一種黃、同一個意思（補充 ADR-0023 §3.1；實作票把它加進 `s0.css` 與 `tests/test_static_css.py` 讀的名單）。
- **寬螢幕（拆出去的面板放在第二個螢幕）：** 可以切成左右兩欄，左邊改之前、右邊改之後，段落對齊；預設仍是一欄。
- **讀起來舒服：** 文章用 `--font-reading-serif`，一行大約 30～35 個中文字；標記不改行高；不放動畫（NFR-OBS-02 的精神）。
- **不只靠顏色分：** 加上的字用 `<ins>`、刪掉的用 `<del>`，刪除線與左邊的記號讓色覺不方便的人也分得出來。
- **為什麼不照字面用紅與綠（待創作者確認）：** 創作者說「像 git 那樣刪掉的紅、加上的綠」，要的是一眼看出改了什麼。這套介面裡紅色的意思是「擋下、失敗」（ADR-0007 §3.2），刪掉的字不是錯；Loomy 也沒有綠色；ADR-0023 §2 已經為同一個畫面選了靛藍與淡灰。所以這裡照 ADR-0023 的兩個 token，用底色、刪除線、左邊的記號做到一眼分得出。創作者看了設計稿還是要紅綠，就另寫一份 ADR 修正 ADR-0023 §2 與 ADR-0007 §3.2，加兩個顏色。

### 3.7 改稿的錢：對話的改稿額度（待創作者確認）

- **問題：** 每一次改稿都是一張要花錢的工單（本機先試，失敗才升到雲端，ADR-0022；一張的上限是費用設定的改稿預算，預設 US$0.50）。寫一篇新文章前有一張最後確認卡（寫預估金額與上限）；改稿現在不問。口述改稿一次會改好幾輪，每輪都跳確認卡太煩，完全不問又可能在沒注意時一直開單。
- **提案：每個對話有一份改稿額度。**
  - 對話裡第一次要改稿時，畫面出一張確認卡：「接下來最多再改 N 次，每次最多 US$X（照費用設定），最多共 US$N×X」，按「好」才開第一張。之後每次改稿從額度扣一次，不再問。
  - 額度用完時，再出同一張卡，按「再給 N 次」才繼續。N 預設 5，在費用設定頁可以改。
  - 額度只由畫面給：畫面入口 `allow_revisions(count)` 由閘道寫進對話資料夾裡一份只增不改的紀錄（`source: ui`），對話的 Pi 叫不到（照 ADR-0025 §3.3 那種只有畫面能叫的入口）。`rewrite` 開單前查剩幾次，沒有了就不開，回一句請創作者在畫面上給額度。
  - **一條規矩管所有改稿：** 打字的「照這個改」與口述的方向都是對話的 agent 叫 `rewrite`，閘道分不出也不該分，所以額度管的是每一次 `rewrite`。這會讓現在打字改稿的第一次多一張確認卡，是行為改變。
  - 對照頂端寫這一輪改了幾次、花了多少、額度還剩幾次。
  - 每月上限、對話同時一張單、每張單的預算照舊（ADR-0021 §3.3、§3.4，ADR-0027 §3.6）。
- **為什麼這樣提：** 第一次就讓創作者看到最壞要花多少，之後不打斷；ADR-0021 §4 列過「一個對話開超過 N 張單要創作者確認」這個方向，這是它在改稿上的版本。創作者要每次都問、或完全不問，改 N 就好（N 設很大就等於不問）。

### 3.8 想法卡：三種處理程度，每一條點得回錄音（P5b）

- **AI 對口述的處理分三種程度，每一條都標出來：**
  1. **只清贅字**：嗯、啊、重複的字拿掉，意思與用詞不動。
  2. **重新排順序**：把散在各處講的同一件事排在一起；標出搬動了哪幾條（原本在第幾句）。
  3. **補了證據或例子**：AI 從這個對話的素材清單、報告與來源補的；標「不是你說的」，並指出補自哪裡。不准從模型的記憶補事實，也不准替創作者補親身經驗（PRD §5、ADR-0025 §3.2 第 3 關的規矩）。
- **每一條都點得回錄音和逐字稿的那一段**（逐字稿帶時間戳，ADR-0028 §3.7）。「補了」的那一條指回它要撐的那句話所在的那一段，另外指出它自己的出處。指不回去的標出來，不假裝有出處（FR-ID-03）。
- 補的那一條不是創作者說的，所以不標 `speaker: creator`，標 `speaker: ai`；仍然是暫定（`status: tentative`）。

### 3.9 追問式訪談的三種模式與回來時的開場摘要（P6）

- **三種模式，隨時可以換**（說一聲或按畫面上的模式標籤）：
  1. **只聽不插話**：AI 不問問題，只簡短表示收到；創作者說「好了」再整理（例如整理成想法卡）。適合邊走邊講。
  2. **追問**：一次一題追問缺口，可以略過、可以「稍後研究」（路線圖 P6 原本的做法）。預設這一種。
  3. **扮反方**：AI 扮演最強的反對意見，壓力測試創作者的論點。畫面上標「AI 扮的反方」，不是 AI 的立場，也不記成創作者的立場；反方用到的事實只能來自報告、來源與素材，沒有就用問句（「如果有人拿出相反的數據呢？」），不編事實。
- 模式記在對話裡；換模式時對話主機通知 agent，跟 `[ef-card]` 一樣。答案要進編輯卡，照舊經訪談的工具與規矩記（ADR-0025）。
- **回到一個對話時的開場摘要：** 創作者離開一段時間（預設 2 小時，可以改；待創作者確認）後再打開一個對話，AI 先用一句話說上次講到哪、還有什麼沒做。
  - 只依記下來的東西說：編輯卡的狀態、跑完與沒跑完的工單、素材清單上還沒處理的附件、等著按的 lesson 提議。不憑印象猜。
  - 一次回來只寫一次，寫成對話裡一則一般的訊息；短時間內重開不再寫。花的是對話的模型錢（`fast`），記在對話的帳本。

### 3.10 記憶的同意照舊在畫面上按

- 會改變創作者之後寫作的記憶，照 lessons 的方式：agent 只能提議，創作者在畫面上按同意，閘道才寫（ADR-0026 §3.3，lessons 的實作見 PR #130）。之後的思想記憶照同一條規矩。這次不改。

## 4. 後果

- **正面：**
  - 手機打開就知道要幹嘛：講、丟、接著聊；桌面專心做長時間的編修，第二個螢幕放對照。
  - 改稿從「打一句、開單、自己勾對照」變成「講一句、直接看修改前後對照」，改了什麼一眼看出；範圍外的修改躲不掉。
  - 每一輪改稿都是一個版本，隨時退得回去；錢在第一次就講清楚最多多少。
  - 想法卡分得出哪句是創作者說的、哪句是 AI 補的。
- **負面：**
  - 手機與桌面的畫面要各做一套版面；拆出去的視窗要跟主視窗同步畫面狀態。
  - 改稿額度讓現在打字改稿的第一次多一張確認卡（待創作者確認）。
  - 範圍外的修改只標不擋：模型常常不守範圍時，創作者要多看、多退版。
  - 開場摘要每次回來花一次對話的模型錢；扮反方的回答要靠畫面標示，不讓人誤以為是查證過的事實。
  - 不照字面用紅綠，創作者看了設計稿可能還是要紅綠（§3.6）。
- **影響範圍：** `src/evidence_forge/ui/`（捕捉畫面、段號、反白範圍、拆出去的面板頁、對照的版面與 `artifacts.py` 的對齊、模式標籤、改稿額度的確認卡）、`static/css/s0.css` 與 `chat.css`（`--diff-outside`）、`tests/test_static_css.py`、`src/evidence_forge/gateway/chat_tools.py`（`rewrite` 的 `scope`、額度檢查、`allow_revisions`）、`chat/`（額度入口、模式通知、開場摘要的時機）、`checks/`（範圍外的比對）、`harness/skills/rewrite/`（範圍外一字不改）、`harness/pi/chat-system-prompt.md`（口述改稿、三種模式、開場摘要）、`cost_settings.py`（N）；PRD FR-MO-05、FR-UI-16、FR-UI-17、FR-RW-05～07、FR-ID-04、FR-DI-01、FR-CH-04、FR-CH-05；`CONTEXT.md` 的口述改稿、修改前後對照、改稿額度、捕捉畫面、創作畫面；待決事項 Q-29～Q-32；路線圖 P5a、P5b、P6、P6b、Later。
