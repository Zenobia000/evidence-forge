# ADR-0024：報告先給下一步與可以寫的題材，文章藏起骨架、不提原作者

> **狀態：** 已接受（創作者 2026-10-15 拍板，見 #100；PR 合併即生效） | **日期：** 2026-10-15 | **決策者：** 專案擁有者
> 依 `docs/templates/vibecoding/04_architecture_decision_record_template.md` 撰寫。
> **修正：** ADR-0020 §3.2 的「分析報告的五節」（換成這裡 §3.1 的五節）與 §3.4 的報告檢查；ADR-0019 背景裡「研究題材的報告」改叫「可以寫的題材」；ADR-0015 的「骨架」從「照著寫的結構」改成「思考的順序，不當標題」。

## 1. 背景與問題

- **上下文：** 創作者 2026-10-15 在聊天室實際讀了一份報告和一篇文章，回饋四件事：
  1. **報告看不懂。** 查證裡的 K1、K2、S3 沒有任何地方解釋；同一件事實在「事實與觀點」和「查證」講兩次；看完不知道下一步要幹嘛。
  2. **研究題材不像「可以寫什麼」。** 現在寫成「原文沒講什麼、去讀哪篇」，是給研究用的；創作者要的是看完別人的觀點、查完證，給他幾個新的發文題材讓他選。
  3. **文章太公式。** 觀點文的骨架（結論先講、論據 1～3、反方說法與回應、結論與行動）被模型直接寫成標題「先講結論」「論據一」「反方怎麼說」「我的建議」。
  4. **文章一直提原作者，像在批判他。** 開頭寫「這篇談的是某某系列…」，反方一節讀起來像在反駁原文。創作者要的是用角色自己的聲音談這個主題，不是回應某篇文章。
- **根因在 skill 的規定，不在程式：** `investigate` 把內部編號（K＝要查的說法、S＝來源）直接放進報告；`rewrite` 叫模型「照骨架寫」，又要它規劃「各來源哪裡同意、哪裡不同意」。
- **為什麼要寫成 ADR：** 報告五節是 ADR-0020 定的，畫面、程式檢查、錄音都照著它；改了要一起動。

## 2. 考量的選項

| 選項 | 結果 |
| :--- | :--- |
| 只改 skill 的措辭，報告五節不動 | 不採用：重複（事實講兩次）與「看完不知道下一步」是結構的問題，改措辭解決不了 |
| 報告保留編號，畫面上加一張編號對照表 | 不採用：創作者讀的是報告本身；編號只對程式有用，留在 `sources.json` 就好 |
| 文章骨架交給角色的文類風格決定，不另外規定 | 不採用：目前只有少數角色校準過文類風格，沒校準的就照骨架寫成標題 |
| **報告改成先給下一步與可以寫的題材；文章把骨架當思考順序、不提原作者** | **採用**（創作者 2026-10-15 拍板） |

## 3. 決策

### 3.1 分析報告的新樣子

```
一句話：這篇在講什麼（第一個 ## 標題之前）
▶ 下一步：下面有 N 個可以寫的題材，說「寫第 2 個」就開始。

## 作者在說什麼      一段，150 字內
## 查證              事實一條一條，每條前面直接標結果，有疑慮的排前面；來源用名字
## 作者的看法        作者的意見，標明不是事實
## 可以寫的題材      3 個，編號；每個：暫定標題、角度一句、原文沒講的、會用到的資料（來源名字）、建議文類
## 來源清單          放最後，畫面上預設收起來
```

- **報告裡不出現 K1、S2 這類編號。** 編號只留在 `sources.json`、`brief.json` 這些給程式讀的檔。內文提到來源一律用名字（標題或發布者）。
- **查證四種標記照 ADR-0023**：【有爭議】【過時】【查不到】【有佐證】，排序也照它（有爭議 → 過時 → 查不到 → 有佐證）。標記後面可以補一句說明（例：「但佐證偏弱」）。
- **「事實與觀點」拆掉。** 事實併進查證，每條事實就是一條查證；觀點獨立成「作者的看法」。
- **可以寫的題材取代研究題材。** 題材是給創作者挑來發文的，不是給研究用的閱讀清單；至少 2 個，有編號，順序跟 `sources.json` 的 `topics` 一樣，「寫第 N 個」就是第 N 個。

### 3.2 文章

1. **文類的骨架只是思考順序，不准當標題。** 標題寫這一節實際在講什麼；「結論」「論據」「反方」「建議」這類骨架字不能當標題。從一個具體的問題或場景切進去，順著想法走到重點，不要第一節就「先講結論」。
2. **內文完全不提原文、不提原作者，也不跟原文對話或反駁它。** 不寫「這篇談的是…」「原作者認為…」，用角色自己的聲音談這個主題。
3. **不要「反方」一節。** 真的重要的另一種看法，自然寫進文中（「有人會覺得…，但…」），不另立標題，也不是反駁原文。
4. **原文仍放在「參考來源」的第一條**（創作者選擇保留），只在清單裡，內文不提。ADR-0020 §3.3 的「一定列原文出處」不變。
5. **創作者選了第 N 個題材，文章就圍繞那個題材寫**，不是圍繞原文的主張。對話的 agent 把那個題材的標題與角度放進 `rewrite` 的目標（`goal`）。

### 3.3 程式檢查（只看格式，不判斷寫得好不好）

- **報告：** 五個新節名依序都在；第一個 `##` 之前有那一句話；全文沒有裸露的 `K<數字>`、`S<數字>` 編號（程式碼裡的不算）；「可以寫的題材」至少 2 個、從 1 起連續編號。來源清單的網址都是這一段真的抓過的，照舊。
- **文章：** 任何一層標題不能是骨架字（以「結論」「論據」「反方」「建議」開頭、或「先講結論」「我的建議」這類）；參考來源以外的內文不能出現原文的標題與原作者名。其餘照舊。

## 4. 後果

- **正面：**
  - 報告先回答「下一步做什麼」，創作者一眼看到可以挑的題材，說一句「寫第 2 個」就能往下走。
  - 同一件事實只講一次；報告裡沒有要對照才看得懂的編號。
  - 文章讀起來是角色自己的一篇，不是對某篇文章的回應或批評。
- **負面：**
  - 報告沒有編號，畫面要把查證一條一條對回 `sources.json`，改成靠順序對（skill 規定查證的順序跟 `fact_checks` 一樣）；模型沒照順序寫時，畫面上那一條的說明可能對錯條。
  - 「沒有裸露編號」只擋這一份真的用到的編號（原文 S1、來源清單上的、關鍵主張），但 `Amazon S3` 剛好碰上來源 S3 時還是會被擋；遇到時在報告裡把產品名包在程式碼記號裡。
  - 「內文不出現原作者名」只比對整個名字（拉丁字母的名字要整個字對上，`Sam` 不會算到 `Samsung`）；原文標題很短時（6 個字以內）不比，以免誤擋。
  - skill 文字改了，`analyze-library`、`rewrite-library` 兩份錄音要重錄。
- **影響範圍：** `harness/skills/investigate/`、`harness/skills/rewrite/SKILL.md`、`harness/genres/opinion.md`、`harness/pi/chat-system-prompt.md`；`src/evidence_forge/checks/analysis.py`、`article.py`；`src/evidence_forge/ui/`（報告面板、結果卡）；PRD §3、§5、§7；`CONTEXT.md` 的研究題材、分析報告、結果卡；`analyze.feature`、`rewrite.feature`。
- **舊報告：** 已經寫好的舊報告（五節是「事實與觀點」「研究題材」那一版）照樣打得開，畫面用它原本的節名顯示，不重跑。
- **重新評估觸發：** 創作者常常要「寫第 N 個」以外的方向（題材挑不到想寫的）；骨架字規則常常擋到正常的標題；或某個角色的文類風格本來就要明寫「結論」這類標題。
