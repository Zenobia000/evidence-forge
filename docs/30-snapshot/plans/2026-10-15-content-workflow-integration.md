# 規劃：把 Sunny 發文工作流併進 Evidence Forge（訪談收斂 → 編輯卡 → 寫稿 → 配圖 → 預覽）

> **日期：** 2026-10-15 | **狀態：** 創作者 2026-10-15 核准 | **來源：** 規劃 session 的計畫檔，下面照原文抄、一字不改（含文末〈2026-10-15 補充〉）；決策拆進 ADR-0025～0027、`CONTEXT.md` 與 PRD（#105）。這份之後只留作紀錄，不再改。

## Context

創作者有兩套東西：

- **Evidence Forge（EF）**：聊天室工作台。丟別人的文章 → brief → 查證 → 分析報告（可以寫的題材）→ 指定角色與文類一次寫成文章。閘道、帳本、預算、Pi、配方與 skill、對話主機、聊天室畫面都已上線（P0～P3）。
- **Sunny 內容流程**（`sunny-content-pipeline-handoff-2026-10-15.zip`）：在 Claude Code 裡逐站對話完成的長文流程，32 篇實戰驗證過。十二站、作者在七個關卡拍板（文體 → 核心觀點 → 只有作者能給的例子 → 邊界 → 工作標題 → 主幹 → 第一人稱與配圖）、`brief.md` 編輯卡是整個流程的狀態、退件寫回 `lessons-learnt.md`、封面／概念圖／數據圖／圖文節奏都有腳本。它自己的交接文件也說：缺的就是一個「有狀態的工作流程引擎」，介面是網頁後台還是對話式 agent 待決定。

創作者要的體驗：**AI 有條理地訪談我、每一步給選項讓我挑或補充；決策過程看得到（我選了什麼、最後的結構與選題）；每篇的素材與圖片都留著可再調；能預覽發出去的樣子。**

結論：EF 就是 Sunny 交接文件裡缺的那個引擎——聊天室當訪談介面、工單資料夾當內容單位、閘道當計費與權限、檢查當關卡。要新做的是「編輯卡＋訪談關卡＋選項 UI＋決策軌跡＋配圖＋預覽」。

## 創作者已拍板（2026-10-15）

1. **文體改用 Sunny 的 7 種＋8 個主題**（essay、research-review、product-case、benchmark、postmortem、explainer、trend），取代 EF 的 12 種。
2. **訪談一關一關問，每關給選項**（3～5 個附理由，可點選或自己補充），選完才往下。
3. **第一個里程碑含配圖**（封面、概念圖、數據圖），不含發布到 Sunny 網站。
4. **規則拆開放**：通用機制（關卡、編輯卡格式、畫圖與檢查腳本）進 repo；品牌內容（聲音、主題主張、標題金句、lessons、色票字型）放 `EF_DATA` 當角色資料，不進 repo。

## 兩套的衝突點與處理

| 衝突 | EF 現在 | Sunny | 處理 |
|---|---|---|---|
| 誰決定 | 重構一次寫完（L4） | 作者每關拍板（L3） | 寫稿前加「訪談」，寫稿只讀編輯卡 |
| 起點 | 只有別人的文章 | 議題、想法、素材都可以 | 三種起點：報告的「寫第 N 個」、自己的想法、貼素材 |
| 文體 | 12 種、只有骨架 | 7 種＋主題，含主證據、搜尋策略、框架、CTA | 換成 7 種；通用定義進 `harness/genres/`，Sunny 價值與 CTA 進角色資料；舊工單的文體照舊顯示 |
| 稿後檢查 | ADR-0020：稿後不檢查內容 | 第 10 站逐句可否證、Truth gate | 機械能查的變檢查（參考資料齊全、圖文節奏、數據圖證據鏈）；可否證性留在訪談最後一關給作者看 |
| 狀態 | 工單只增不改，每版一張新單 | `brief.md` 一直改 | 編輯卡放在對話底下，決策是只增不改的事件；寫稿工單帶一份當時的編輯卡快照 |
| 調研 | 查證原文的說法 | 替作者的主張找證據（來源分層、跨地區） | 第二階段加「為主張找證據」的配方，沿用 investigate 與 Tavily |
| 配圖 | 沒有 | 五支腳本＋生圖 | 腳本收進 repo 套件，經閘道的 `run_script` 執行；生圖要經閘道計費 |

## 目標流程

```
起點（報告的第 N 個題材｜我的想法｜貼素材）
 → 訪談（聊天室，一關一關給選項）
     1 文體＋主題 → 2 核心觀點（命名）→ 3 只有你能給的例子 → 4 邊界
     → 5 工作標題 → 6 框架、主幹與圖文分鏡
     每一關：AI 列 3～5 個選項＋理由 → 創作者點一個或補充 → 記進編輯卡
 → 寫稿工單（讀編輯卡快照＋報告與來源＋角色）→ article.md（含圖位）
 → 配圖工單（封面、概念圖、數據圖；check_layout）→ images/、charts/
 → 預覽（網站版型）→ 改稿＝新版本，退件意見提議寫進 lessons
```

## 2026-10-15 補充二（不在原計畫檔裡：PR #118 第一輪審查時，創作者接著拍板的四件）

1. **問題卡照 Claude Code、Codex CLI 規劃模式問釐清問題的樣子做。** 每一關用 1～4 張問題卡，一次出一張、照順序；每張有短標籤、問題、2～4 個選項（名稱加說明）、一定有的「其他」自由回答，選了選項可以附補充；答完出下一張。
2. **要重確認的關可以按「沿用」。** 這是決策紀錄的第三種事件（哪一關、保留哪個決定），由畫面的按鈕經閘道寫。
3. **「照這張編輯卡寫稿」只在六關都有決定、沒有要重確認時才出現。** 寫稿工具的拒絕留著當最後一道關。
4. **舊的技術不必支援。** 舊資料留在硬碟上，但新程式不支援舊格式：不做 12 種舊文類的顯示對照，舊格式的報告與文章不做特別顯示，舊工單只要不讓畫面壞掉（照原字顯示或列成「舊格式」）。這一條取代上一段〈2026-10-15 補充〉第三點的「舊的 12 種文類一律對應到新的 7 種」。

決策寫在 ADR-0025（問題卡、沿用、寫稿按鈕）與 ADR-0026 §3.4（舊的技術）。

## 2026-10-15 補充三（不在原計畫檔裡：同一天稍晚，創作者再拍板的兩件）

1. **一關的問題卡一起送出。** 創作者把這一關的卡都答完（送出前可以回頭改任何一張），再按「確認並送出這一關」。一關送出一次；事件仍可以一張卡一筆，但在送出時一批寫進去。
2. **創作者點的東西由系統記，不由 agent 轉述。** 問題卡送出的回答、「沿用」、「重問這一關」都是畫面 → 閘道，閘道直接寫進決策紀錄，再像 `[ef-job]` 那樣通知對話的 agent 接著往下。agent 只提出問題卡與讀編輯卡；創作者改在主輸入框打字回答時，agent 解讀之後可以用一個另外的工具記下來，事件標 `source: agent`，跟畫面記的 `source: ui` 分開。

決策寫在 ADR-0025 §3.2、§3.3。

## 2026-10-15 補充四（不在原計畫檔裡：創作者 2026-10-15 依設計理念逐條確認 A～G）

創作者把 PR #118 列出的七個判斷，照設計理念逐條看過，全部確認：

- **A** 第 3 關一定等作者；「你幫我選」只選不需要作者經驗的文體。
- **B** 無人看管的自動投入只跑到分析報告。
- **C** 稿後只做機械能查的檢查，加上寫之前在第 6 關給創作者看的主張清單；稿後不用模型查內容。
- **D** 「內文不提原文」只在從分析報告開始時適用，**但文體是 `essay`（有感而發）時例外**：隨筆可以在內文引用並回應觸發它的原文。其他文體從報告開始，內文照舊不提原文，原文照樣列在參考來源第一條。
- **E** 數據圖的數字找不到真的抓過的來源或作者素材，就不畫，並告訴創作者是哪一個數字沒有出處。
- **F** 配圖是單獨一張工單；改稿後沿用封面，除非說「換封面」；概念圖與數據圖只在內容改了才重畫。
- **G** lessons 由 agent 提議、創作者在畫面上同意、閘道寫入；標題與金句、句型這類規則放在各角色的 `craft/`，`data/style/` 的共用檔只當沒有時的備用。
